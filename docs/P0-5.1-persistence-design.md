## A. 决策：SQLite + 事件溯源 (event-sourcing) 追加表

### A.1 选 SQLite，不选 PostgreSQL

按“桌面端单进程量化控制台”这个产品形态做的取舍：

1. **单进程部署**：当前 `services/control-api` 跑在同一台机器上，由 Electron 桌面壳启动；没有第二台机器写入。多写入并发不存在 → 不需要 Postgres 的 MVCC + 多连接调度能力。
2. **零运维负担**：Postgres 需要单独安装、维护服务、配置 `pg_hba.conf`、做 backup/restore；SQLite 只是 `.sqlite3` 文件 + WAL 日志，与现有 `state.json` 同样可以被 git 之外的目录持有。Electron 应用对“双击安装即可用”有强约束。
3. **电池/离线友好**：SQLite 完全本地、无 socket、无后台进程。桌面端在无网络环境也能跑回测、看历史。
4. **WAL 模式给读不阻塞写**：开 `PRAGMA journal_mode=WAL`，读连接和写连接互不阻塞，足以支撑当前的并发量级（1 个 FastAPI 主写线程 + N 个 SSE / 读取连接）。
5. **Python 内置**：`sqlite3` 在 stdlib，无新依赖。当前 `requirements.txt`（如有）不增加体积。

**容量考量**：

- 现 `state.json` 大小 3 MB，主要是 `audit_events`（8 条样本）+ `market_details` + 历史快照。
- 真上线后，`audit_events` 量级粗估为 1-5 万条/月（手动交易 + 后台 reconcile + 提醒）。SQLite 单库到几 GB 仍很顺畅，远早于触达 SQLite 的 281 TB 上限。
- 如果未来真的扩到多机或多写入，迁移到 Postgres 的 schema 改动很小（除了 `INTEGER PRIMARY KEY AUTOINCREMENT` 要换成 `BIGSERIAL`），因为本设计的所有 schema 都不依赖 SQLite 私有特性。

### A.2 选事件溯源 (append-only)，不选 JSON 文档存储

为什么不继续走 “一份大 JSON 文档” 的路线：

1. **需要范围查询**：审计页要按时间倒序拉最近 100 条 `ExecutionEvent`；策略活动二级窗要按 `strategy_id` 拉相关事件；新闻页按 `severity in ('P0','P1')` 过滤。这些都是关系型查询，JSON 文档每次只能整体扫描，O(N) 不可接受。
2. **需要 schema 强类型**：Round 50 修的 “参数从编辑器到运行态/回测” 多口径问题（见 `docs/生产级真实量化交易系统剩余开发清单-2026-04-20.md` §6.3）的根因是 JSON 内部字段漂移。SQLite 的 `CREATE TABLE` + `CHECK` 约束能从源头避免类似问题。
3. **审计需要不可变性**：`audit_events` 表必须是 append-only，任何写入都新增一行；用 SQL 的 `CREATE TRIGGER` + 缺少 `UPDATE`/`DELETE` 权限可以强制这一点。JSON 文档没有这个机制。
4. **快照与事件分离**：`ChangeRequest`、`AgentJob`、`BacktestRun` 这些是“当前状态 + 历史变迁”的混合体；事件溯源天然能让“当前快照”和“历史 trail”分两套表存放，不混在一起。

事件 vs 快照的存储边界：

- **append-only 事件表**：`audit_events`、`execution_events`、`parameter_versions`。这些表只 INSERT，不 UPDATE / DELETE。删除需走归档 (§E) 流程。
- **当前快照 + 历史表**：`change_requests`、`agent_jobs`、`backtest_runs`、`config_snapshots`。当前快照表存“最新一行”，每次状态推进同时插入事件表的一条历史记录。

## B. 表结构 (DDL 草图)

DDL 用 SQLite 语法。所有表都默认 `STRICT` 模式 + `WITHOUT ROWID` 当主键不是 `INTEGER` 时显式声明。所有时间字段用 ISO8601 字符串（与现有 `OrderRecord.created_at` 习惯一致），不用 Unix epoch，方便人眼调试 `.sqlite3` 文件。

### B.1 `audit_events`

事件溯源主表。对应当前 `models.py:1733 ExecutionEvent`。

```sql
CREATE TABLE audit_events (
    id              TEXT PRIMARY KEY,        -- ULID, 时间排序
    event_type      TEXT NOT NULL,           -- e.g. "exchange_order.created"
    severity        TEXT NOT NULL CHECK (severity IN ('INFO','WARNING','ERROR')),
    source          TEXT NOT NULL,           -- "quant-core" / "desktop" / "openclaw" / "system"
    symbol          TEXT,
    strategy_id     TEXT,
    payload_json    TEXT NOT NULL,           -- 序列化的 dict
    summary         TEXT,                    -- repo._build_audit_event_summary 预计算
    impact_detail   TEXT,
    priority        INTEGER NOT NULL DEFAULT 6,  -- 1-9，越小越关键
    is_key_event    INTEGER NOT NULL DEFAULT 0 CHECK (is_key_event IN (0,1)),
    trace_id        TEXT,
    occurred_at     TEXT NOT NULL,
    created_at      TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ','now'))
) STRICT;

CREATE INDEX idx_audit_events_occurred_at  ON audit_events(occurred_at DESC);
CREATE INDEX idx_audit_events_strategy     ON audit_events(strategy_id, occurred_at DESC);
CREATE INDEX idx_audit_events_event_type   ON audit_events(event_type, occurred_at DESC);
CREATE INDEX idx_audit_events_severity     ON audit_events(severity, occurred_at DESC);
CREATE INDEX idx_audit_events_priority_key ON audit_events(priority, is_key_event, occurred_at DESC);

-- 强制 append-only:
CREATE TRIGGER audit_events_no_update
BEFORE UPDATE ON audit_events
BEGIN
    SELECT RAISE(ABORT, 'audit_events is append-only');
END;

CREATE TRIGGER audit_events_no_delete
BEFORE DELETE ON audit_events
BEGIN
    SELECT RAISE(ABORT, 'audit_events is append-only; use archive flow');
END;
```

`SettingsPayload` 与 `WorkspacePreferences` 的快照，用于审计排查“某天起这个 key 改了”。

## C. 迁移策略

按四步走，每一步都可独立回退。所有改动落在新目录 `services/control-api/persistence/`，不修改 `repository.py` 接口签名（`AppRepository.snapshot()` / `add_event()` / `_persist()` 仍然存在）。

### C.1 Step 1: 建 schema + 迁移 runner

新增文件结构：

```
services/control-api/persistence/
  __init__.py
  connection.py        # SQLite 连接池、WAL 设置
  migrations/
    001_initial.sql    # 上面 §B 的所有 CREATE TABLE
    002_*.sql          # 后续增量
  runner.py            # 检查 schema_migrations，按序应用
  dao_audit.py         # 每张表一个 DAO
  dao_change_request.py
  dao_agent_job.py
  dao_backtest.py
  dao_execution_event.py
  dao_parameter_version.py
  dao_config.py
```

DAO 只暴露纯 CRUD（insert / get / list / update_status），不含业务逻辑。

启动时：

1. 如果 `.runtime/control.sqlite3` 不存在，runner 创建并跑全量 migrations。
2. 如果存在但 `MAX(version) < target`，应用增量 migration 文件。
3. 如果 `MAX(version) > target`（用户回滚了代码），refuse to start，提示用户先升级或恢复 backup。

**测试覆盖**：建一份 `tests/test_persistence.py`，全量跑 migrations 到内存数据库，断言所有表的 schema 与预期一致。

### C.2 Step 2: 双写

`AppRepository._persist()` 现在只写 `state.json`。Step 2 保持 `state.json` 写入不变，**额外**把每个写入操作映射到 SQLite。

实现要点：

- `repo.add_event(...)` → 在写 `state.audit_events.append(...)` 后追加 `dao_audit.insert(event)`。
- `repo.create_change_request(...)` → 写 `state.change_requests` + `dao_change_request.upsert(...)` + `dao_change_request.insert_history(...)`。
- 双写失败策略：SQLite 写失败时，warning 级日志 + 把 `state.json` 视为 source of truth；不阻塞 API 请求返回。这样可以在生产中安全观察一段时间，把 SQLite 的稳定性从 0 升到 9。

观察手段：
- 新增 `GET /api/internal/persistence/diff`（仅本地访问），逐表 diff `state.json` 与 SQLite 的关键计数。
- 跑现有 444 条集成测试，确认 SQLite 的写入路径不破坏旧路径。

### C.3 Step 3: 切读

读路径开始优先消费 SQLite。`AppRepository.snapshot()` 内部从 SQLite 拼出 `AppState`，`state.json` 仅作为审计文件保留。

切读顺序（按风险递增）：

1. **`audit_events`**：最简单，只追加，没复杂事务。
2. **`backtest_runs`**：写入频率低，结构简单。
3. **`change_requests` + `agent_jobs`**：联动，要一起切。
4. **`parameter_versions`**：影响策略参数读取，最后切。
5. **`config_snapshots`**：低频改动，可独立切。

每一步切读后，跑一周观察是否有 schema drift（SQLite 缺字段时 DAO 应当显式回退到 `state.json` 兜底，不直接抛异常）。

### C.4 Step 4: 停 `state.json` 写入

所有读路径已稳定切到 SQLite 后，关闭 `_persist()` 对 `state.json` 的写入；保留 `.runtime/state.json.snapshot.{date}` 作为最后的迁移点，方便回滚。

`state.json` 文件本身不删除，保留作为冷归档（git ignore，不影响仓库）。

## D. 并发模型

### D.1 WAL + 连接池

启动时一次性配置：

```python
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA synchronous=NORMAL")     # WAL 下 NORMAL 已足够安全
conn.execute("PRAGMA foreign_keys=ON")
conn.execute("PRAGMA busy_timeout=5000")      # 5s 写锁等待
```

连接管理：每个线程持有自己的 `sqlite3.Connection`。FastAPI 的请求线程通过 `threading.local()` 拿连接；后台 `strategy_runtime_thread` 与 `agent_worker_thread` 各自独立连接。

写竞争：SQLite 写永远是单串，靠 `busy_timeout` 让等待者排队，不主动控制。

### D.2 事务边界

下面这些操作必须落在同一事务（BEGIN ... COMMIT）：

| 业务操作 | 同事务包含的写入 |
| --- | --- |
| 提交 `ChangeRequest` 并落地 | `change_requests.upsert` + `change_request_history.insert` + `audit_events.insert` |
| 编辑策略参数 | `parameter_versions.insert` + `change_requests.upsert(if any)` + `audit_events.insert` |
| ExecutionEngine 状态迁移 | `execution_events.insert` + `audit_events.insert(if user-visible)` |
| 回测完成 | `backtest_runs.update(status='completed')` + `agent_jobs.upsert(generate_backtest_review)` + `audit_events.insert` |
| Agent job 状态推进 | `agent_jobs.update` + `audit_events.insert` |

事务封装由 DAO 上层的 “use case” 函数负责（不在每个 DAO 里 BEGIN）。原型期可以提供一个 `with PersistenceUnit() as unit:` 上下文管理器。

### D.3 与现有 RLock 的关系

当前 `AppRepository._lock = RLock()` (`repository.py:148`) 保护 `self.state` 这个内存对象 + `self.path` 写入。引入 SQLite 后：

- **过渡期 (Step 2 双写)**：`RLock` 仍持有，`with self._lock:` 块内同时调 SQLite DAO。SQLite 自身的 `busy_timeout` 是兜底，不依赖 RLock。
- **稳定期 (Step 3 切读后)**：`RLock` 仍保留，因为 `self.state` 内存对象（snapshot 缓存）仍存在。但临界区会显著缩短：只在内存缓存刷新时持锁，业务写入直接走 SQLite 事务。
- **长期 (state.json 完全废弃)**：`AppRepository.state` 缓存可能被去掉，每次 `snapshot()` 直接拼 SQLite；`RLock` 也可以退役。这是较远期的事，本设计文档不强求。

## E. 备份与恢复

### E.1 快照策略

利用 SQLite 的 `BACKUP API` 做 hot backup（不停服）：

- 桌面端在每天 03:00 自动跑一次 `BACKUP control.sqlite3 → backups/control-{YYYY-MM-DD}.sqlite3`。
- 保留最近 14 天日备 + 最近 12 个月的月初备份。
- 备份目录默认在 `services/control-api/.runtime/backups/`，可在 `SettingsPayload` 中改路径。

也支持手动触发：新增 `POST /api/internal/persistence/backup`（仅本地访问，无 auth），桌面端 “设置 → 数据” 面板提供按钮。

### E.2 恢复流程

1. 停止 `services/control-api`。
2. 把 `backups/control-{date}.sqlite3` 复制为 `.runtime/control.sqlite3`。
3. 启动服务；migration runner 检查 `schema_migrations` 版本：
   - 若备份是更老版本 → 自动应用增量 migrations，恢复完成。
   - 若备份是更新版本 → refuse to start（防止数据被旧代码覆盖）。
4. 若 `state.json` 仍存在（过渡期），引擎以 SQLite 为准；`state.json` 的内容会被 next `_persist()` 覆盖回与 SQLite 一致的内容。

### E.3 schema 迁移回滚

- 默认提供 forward migration only（`001_*.sql` → `002_*.sql` → ...）。
- 每个 migration 同时提供配对的 `001_*.down.sql`（可选）。下行迁移仅在测试中用，生产不鼓励运行（事件溯源数据 down 后无法还原）。
- 若必须回滚到旧 schema，标准流程是 “停服 + 备份还原 + 旧版本启动”，而不是跑 `down.sql`。

> TBD: needs prototyping — `down.sql` 的有用性需评估。某些表（如 `audit_events`）下行后不可能还原数据，可能需要约定 “破坏性迁移不提供 down”。

### E.4 损坏检测

- 每次启动跑 `PRAGMA integrity_check`；输出 `ok` 才允许继续。
- 失败时拒绝启动，提示用户从 backup 恢复。
- WAL 文件损坏不算严重（WAL 自带 checksum）；但主库损坏要走完整恢复流程。

## F. 测试策略

### F.1 单元测试：内存 SQLite

- `tests/test_persistence.py` 全量用 `sqlite3.connect(":memory:")`，避免磁盘 IO。
- 每个 DAO 覆盖 insert / get / list / update / boundary（unique constraint 重复 / FK 失效 / CHECK 违反）。
- `runner.py` 的 schema_migrations 边界：跑空库 → 应用全量；跑已有部分 → 应用增量；跑新版本数据库 + 旧代码 → 拒绝启动。

### F.2 集成测试：tempfile SQLite

- 每个测试用 `tempfile.NamedTemporaryFile(suffix=".sqlite3")` 起一份独立数据库，模拟真实磁盘行为（WAL、busy_timeout）。
- 双写测试：构造 `AppRepository(path=temp_state_json, sqlite_path=temp_db)`，跑一系列 `add_event` / `create_change_request`，断言 `state.json` 与 SQLite 内容等价。
- 启动恢复测试：在 SQLite 中手工塞入构造好的不一致数据，断言 `AppRepository.__init__` 的 reconcile 逻辑做出正确选择。

### F.3 迁移测试

- forward migration：001 → 002 → 003 全部跑通，每步后检查 `schema_migrations` row + 关键表存在。
- 跨版本启动：模拟用户从 v1 升级到 v3，断言中间 v2 的迁移自动应用，并保留 v1 的数据。
- 损坏库恢复：手工破坏 SQLite 文件（写入随机字节），断言 `PRAGMA integrity_check` 失败并拒绝启动。

### F.4 并发回归

- 起 4 个线程同时 `add_event`，断言所有事件都落入 `audit_events` 且无重复 id。
- 模拟一次写入 + 一次 SELECT 并发，断言 SELECT 在 WAL 模式下不被阻塞（用 `time.monotonic()` 测量）。
- ExecutionEngine 状态机迁移并发：两个线程对同一 `intent_id` 同时尝试 `state_to = ACKED`，断言只有一个成功（依赖 `UNIQUE (intent_id, state_to, occurred_at)` 约束 + 应用层重试）。

### F.5 现有测试保护

- 跑完全量 444 条 `tests/test_control_api.py` 后，总耗时增长不超过 30%（SQLite 在内存或临时文件上比 JSON parse 快，但 fixture 起停可能慢）。
- 任何 `tests/test_control_api.py` 用例失败 = 持久化层引入了行为差异，必须修引擎，不修测试。

## G. 开放问题

1. **`state.json` 的真实大小峰值** — 现状 3 MB（demo 数据少）；生产真上线 6 个月后审计事件可能膨胀到 100 MB。需要 prototype 一次完整回放，确认 SQLite 表大小与查询延迟在 `audit_events` 1M 行下仍 < 100ms。
2. **`result_blob` 是否拆表** — 当前设计把 `BacktestRun` 的 trades 明细存在单 `result_blob` TEXT 列。若桌面端要做 “按 trade 维度过滤 / 排序”，必须拆 `backtest_run_trades` 子表。当前 UI 没有这种需求，但 P0-4.4 回测引擎可能要求。
3. **`feature_flags` 配置位置** — P0-4.2 设计要求 ExecutionEngine 用 `settings.feature_flags`；本设计把它放进 `config_snapshots(snapshot_kind='feature_flags')`。两边对 “当前 flag 怎么读” 还没统一接口；可能需要一个 `dao_feature_flags.get_current()` helper。
4. **多设备同步** — 长期看，桌面端可能跨多台机器（家里 + 公司）。SQLite 本地存储无法天然同步；需要单独的同步层（Litestream / S3 / iCloud Drive）。当前 P0/P1 不处理，但 schema 设计要避免依赖单机假设（所有 PK 用 ULID/UUID 而非自增 INTEGER）。
5. **审计事件归档** — `audit_events` 长期增长后，桌面端审计页查询会变慢。需要决定 “> 90 天的事件是否归档到独立表 / 独立文件 / 直接 DELETE（违反 append-only）”。倾向归档到 `audit_events_archive_{year}.sqlite3` 单独文件，主库只保留近 90 天，但需要 prototype 验证查询体验。
6. **`AppState.market_details` 的去向** — 当前 `state.json` 包含 4 个 watchlist symbol 的 `MarketDetail`（K 线、盘口、recent trades）。这部分是**缓存**，不是事实源，理论上不应该进 SQLite。本设计暂不为此建表，由 `BybitPublicMarketClient` 用 in-memory dict 兜底；但桌面端 cold start 时可能短暂空白，需要 UX 上接受这一点。
7. **跨表 transaction 与 SQLite 的 `BEGIN IMMEDIATE` 选择** — 双写期事务跨 `state.json` 和 SQLite 两套存储，无法做真正的 atomic commit；如果 SQLite 写成功但 `state.json` 写失败，状态会不一致。可能需要约定 “SQLite 永远是真理，`state.json` 失败不算失败”，但这与 Step 2 的双写承诺矛盾。需要明确策略。
