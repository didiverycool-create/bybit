## A. 方法学

### A.1 被测对象

`services/control-api/persistence/migrations/001_initial.sql` 中 §B.1 `audit_events` 表与五个二级索引:

- `idx_audit_events_occurred_at  (occurred_at DESC)`
- `idx_audit_events_strategy     (strategy_id, occurred_at DESC)`
- `idx_audit_events_event_type   (event_type,  occurred_at DESC)`
- `idx_audit_events_severity     (severity,    occurred_at DESC)`
- `idx_audit_events_priority_key (priority, is_key_event, occurred_at DESC)`

加 `BEFORE UPDATE` / `BEFORE DELETE` trigger (append-only 强制)。

### A.2 基准脚本

`services/control-api/persistence/benchmarks/bench_audit_events.py` (新增于本轮)。

要点:

1. 使用 `tempfile.NamedTemporaryFile(suffix=".sqlite3", delete=False)` 起一份**真实磁盘**的 SQLite 文件 (不是 `:memory:`), 与生产 `.runtime/control.sqlite3` 同一行为。
2. 通过 `persistence.connection.connect()` 打开连接, 与生产路径一致 (WAL + `synchronous=NORMAL` + `foreign_keys=ON` + `busy_timeout=5000`)。
3. 执行 `MigrationRunner` 以应用 `001_initial.sql`。
4. 插入 1,000,000 行合成 `audit_events`, 数据分布:
   - 30 个 `event_type` (粗略对应生产集: `exchange_order.*`, `strategy.*`, `risk.*`, `channel.*`, `backtest.*`, `agent.*`, `system.*`)。
   - 50 个 `strategy_id` (`strat-000` … `strat-049`), 5% 行 `strategy_id` 为 `NULL`。
   - 8 个 `symbol`, 15% 行 `symbol` 为 `NULL`。
   - `severity`: 70% INFO / 25% WARNING / 5% ERROR。
   - `priority` 1-9 均匀; `is_key_event` 仅当 `priority<=3` 时 50% 概率为 1。
   - `occurred_at` 在过去 180 天内均匀分布。
   - `payload_json` 目标 ~500 字节, 用 `random` 字符填充实现。
5. 插入用 `executemany` + 10,000 行一批, 每批一个事务 (`with conn:` 隐式 BEGIN/COMMIT) 避免大事务的 WAL 抖动。
6. 插入完成后, 主动 `PRAGMA wal_checkpoint(TRUNCATE)` 与 `ANALYZE`, 让查询阶段不被未 checkpoint 的 WAL 主导, 也让 query planner 有最新统计信息可用。
7. 七条桌面端常用查询每条跑 100 次, 每次绑定参数随机化, 记录 min / P50 / P95 / P99 / max。
8. 对每条查询额外捕获一次 `EXPLAIN QUERY PLAN`, 用于诊断索引利用率与 seq-scan。
9. 全程在 `try/finally` 里清理 `.sqlite3` / `.sqlite3-wal` / `.sqlite3-shm` 临时文件。

### A.3 硬件 / 软件

```
platform : macOS-26.4.1-arm64-arm-64bit
python   : 3.9.6 (default, Apr 7 2026, 02:38:40)  [Clang 21.0.0 (clang-2100.0.123.102)]
sqlite   : runtime=3.51.0 module=2.6.0
target   : 1,000,000 rows, batch=10,000
queries  : 7 query types × 100 runs each
budget   : P95 < 100ms (per design G.1)
```

固定随机种子 (`RANDOM_SEED = 20260427`), 同一台 Mac 重跑结果可复现。

## B. 插入阶段结果

| 指标 | 实测 |
| --- | --- |
| 总行数 | 1,000,000 |
| 总耗时 | 312.04 s |
| 吞吐 | **3,205 行/s** |
| 批数 | 100 (每批 10,000 行) |
| 每批耗时 min / P50 / P95 / max (ms) | 1005.7 / 2756.2 / 3018.9 / 3106.7 |
| 主库文件大小 | 1049.2 MiB (≈ 1.0 GiB) |
| WAL 文件大小 (checkpoint 前) | 2.8 MiB |

观察:

- 平均每行 **~1.05 KiB** 写入, 与设计预期 (~500 字节 payload + 索引 + 行头) 大致吻合。
- 第一批完成耗时 ~1s, 之后稳定在 ~3s/批; 慢化的来源主要是索引在 1M 行下重新平衡 B-tree 节点。
- 吞吐比设计的 100 events/s (P0-design-decisions-2026-04-26.md J.1 备注) 高 **30 倍以上**, 不构成瓶颈。

## C. 查询阶段结果

每条查询 100 次, 单位毫秒 (ms)。

| 查询 | 描述 | min | P50 | P95 | P99 | max | 是否 < 100ms |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Q1 | `ORDER BY occurred_at DESC LIMIT 50` (审计页最近) | 0.08 | 0.09 | 0.14 | 0.33 | 0.34 | **PASS** |
| Q2 | `WHERE strategy_id = ? ORDER BY occurred_at DESC LIMIT 100` (策略活动) | 0.20 | 0.36 | 0.48 | 0.72 | 0.93 | **PASS** |
| Q3 | `WHERE severity='ERROR' AND occurred_at >= ? ORDER BY occurred_at DESC LIMIT 100` (告警摘要) | 0.18 | 0.20 | 0.25 | 0.38 | 0.52 | **PASS** |
| Q4 | `WHERE event_type = ? ORDER BY occurred_at DESC LIMIT 50` (事件类型筛选) | 0.10 | 0.13 | 0.23 | 0.40 | 0.43 | **PASS** |
| Q5 | `SELECT COUNT(*) WHERE occurred_at >= ?` (区间计数) | 0.09 | 4.33 | **27.47** | 29.40 | 34.48 | **PASS** |
| Q6 | `WHERE priority<=3 AND is_key_event=1 ORDER BY occurred_at DESC LIMIT 50` (高优关键事件) | 0.18 | 0.19 | 0.28 | 0.49 | 0.90 | **PASS** |
| Q7 | `GROUP BY strategy_id ORDER BY 2 DESC LIMIT 20` (策略活跃排行) | 44.39 | 45.73 | **47.06** | 52.01 | 52.19 | **PASS** |

最大 P95 是 Q7 的 47.06ms — 仍在预算之内的一半位置。

### C.1 EXPLAIN QUERY PLAN

```
Q1_recent_50:
  SCAN audit_events USING INDEX idx_audit_events_occurred_at

Q2_strategy_recent:
  SEARCH audit_events USING INDEX idx_audit_events_strategy (strategy_id=?)

Q3_severity_error_recent:
  SEARCH audit_events USING INDEX idx_audit_events_severity (severity=? AND occurred_at>?)

Q4_event_type_recent:
  SEARCH audit_events USING INDEX idx_audit_events_event_type (event_type=?)

Q5_count_since:
  SEARCH audit_events USING COVERING INDEX idx_audit_events_occurred_at (occurred_at>?)

Q6_priority_key_events:
  SCAN audit_events USING INDEX idx_audit_events_occurred_at

Q7_per_strategy_count:
  SCAN audit_events USING COVERING INDEX idx_audit_events_strategy
  USE TEMP B-TREE FOR ORDER BY
```

### C.2 索引利用率讨论

- **Q1 / Q2 / Q3 / Q4 / Q5**: 全部走索引, 都是 SEARCH 或 (在 ORDER BY 主键上) 顺扫前 N 条的形态, 是最理想的形状。
- **Q5** 的 `COVERING INDEX` 标记意味着 SQLite 不回主表, 完全在索引上完成; 这是 P95 ~27ms 的来源 (扫描索引区段 + COUNT 聚合)。
- **Q6** 走 `idx_audit_events_occurred_at` 顺扫 + 谓词过滤 (`priority<=3 AND is_key_event=1`)。这里 *没有* 走 `idx_audit_events_priority_key`, 因为该索引以 `priority` 为前缀, 而我们要 `ORDER BY occurred_at DESC LIMIT 50` —— 顺着时间倒序索引扫前 N 条更便宜。SQLite 选错的可能性此处不存在: 实测 P95 0.28ms, 已经够低。
- **Q7** 是唯一需要 TEMP B-TREE 的查询 — `GROUP BY strategy_id` 后再 `ORDER BY COUNT(*) DESC LIMIT 20`, 必须在临时 B-树上排序聚合结果。它扫描整个 `idx_audit_events_strategy` covering index (1M 行) 完成 GROUP BY, 是 P95 47ms 的根因。这条查询是当前 7 条里**最贵的**, 但仍 < 50ms。

### C.3 没有 seq-scan

七条查询都没有触发 `SCAN audit_events` (主表顺扫)。所有 SCAN 都是在索引或 covering index 上的 (Q1 / Q6 / Q7), 不读主表数据页。

## D. 验收 / 决策

### D.1 P0-5.1 §G.1 / P0-design-decisions-2026-04-26.md G.1

> "用 1M 行 audit_events 模拟数据填充 SQLite。
> 跑桌面端审计页常用查询 (按 strategy_id 倒序拉 50 条 / 按 severity 过滤)。
> 验收标准: P95 查询延迟 < 100ms。"

**结论: 全部通过。** 7/7 query 的 P95 都 < 100ms, 且最高 P95 (Q7 = 47.06ms) 低于预算的一半。

### D.2 90 天归档策略 (G.5) 是否要从 wave-4 提前到 wave-2

**推荐: 不需要提前。** 保留 G.5 的原计划 — 在 wave-4 实施 `audit_events_archive_{year}.sqlite3` 归档。

理由:

1. 1M 行下 P95 全部达标且大量裕度。1M 行对应 P0-5.1 §A.1 估算的 "1-5 万条/月" 的约 20-100 倍, 即覆盖至少 1-2 年的生产数据。
2. 数据库文件 ~1 GiB, 远低于 SQLite 281 TB 的极限以及现代 macOS 桌面端可用磁盘空间。
3. 主要瓶颈是 Q7 的 GROUP BY (扫整个 covering index)。这条查询不在审计页热路径上 — 桌面端 "策略活跃排行" 可以做后端缓存或离线计算, 即使数据增长 10x 到 10M 行, P95 大概率仍在数百毫秒级别, 不算用户可感的卡顿。
4. 主路径查询 (Q1-Q4, Q6) 的 P95 全部在 1ms 量级, 基本与索引深度成对数关系增长 — 即使再增长 10x 到 10M 行, 也只会膨胀到 3-5ms 水平, 仍远低于 100ms 预算。

### D.3 何时复议

仍按 P0-design-decisions-2026-04-26.md G.1 / G.5 的 "复议时机" 触发:

- 如果生产部署 6 个月后实际 `audit_events` 增长速度大于预期 (>50 万行/月, 而非估算的 1-5 万/月), 提前再做一次 1M / 5M / 10M 行的回放压测。
- 如果将来引入更复杂的查询 (例如审计页要做按 `payload_json` 关键字全文搜索), 需要单独评估 (本压测不覆盖 LIKE / FTS 路径)。
- 如果用户反馈 "策略活跃排行" 卡顿 (Q7 类查询), 在落地归档前先尝试给该查询加 covering index 或缓存层。

## E. 异常 / 注意事项

1. **insert 吞吐 (3,205 行/s) 看着不高, 但够用。** 生产估算每月 1-5 万事件 (P0-5.1 §A.1) 折合每秒 0.02-0.2 行, 比本压测低 4 个数量级。压测中的吞吐受限于 `executemany` 内部循环 + 索引平衡, 不是 SQLite 写盘瓶颈; 生产单事件写入 ms 级别, 压测的 "每行平均 312μs" 数字不能直接外推。
2. **`PRAGMA wal_checkpoint(TRUNCATE) + ANALYZE` 在查询阶段开始前调用。** 这是因为生产环境通常会在桌面端启动后自然 checkpoint (idle 时段触发); 不主动 checkpoint 会让查询的 P99 包含 WAL 解析时间, 不真实地放大延迟。
3. **`payload_json` 平均长度 ~500 字节, 与生产实际可能略有出入。** 真生产路径下, `ExecutionDecision` / `RiskDecision` 序列化大小可能在 800-1500 字节区间。但本压测 7 条查询里, 没有任何查询消费 `payload_json` 内容 (只 `SELECT *` 把它取回来), 所以 payload 大小对查询 P95 的影响主要是 IO 量。即使 payload 翻 3 倍, P95 也只会按比例略增 — 不影响 < 100ms 验收。
4. **macOS 26.4.1 + APFS 在 SSD 上的 fsync 表现** 决定了 insert 阶段的 WAL 落盘速度; 不同硬件上 (Linux ext4 / NVMe) 吞吐可能更高, 但查询 P95 主要由内存中 B-tree 访问主导, 跨平台差异有限。
5. 整个压测脚本运行总时长 ≈ 5 分 16 秒 (大部分在 insert), 在题目要求的 5 分钟附近 — 是预期范围。
