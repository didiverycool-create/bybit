# 开发约定

本文档用于帮助后续 AI 会话、Codex 新线程或人工开发者快速接手当前项目。

## 1. 先读什么

新线程进入仓库时，建议按以下顺序阅读：

1. `AGENTS.md`
2. `README.md`
3. `docs/架构总览.md`
4. `docs/接口契约.md`
5. `docs/实施路线与接手清单.md`
6. 当前要改动的代码文件

## 2. 改动前先判断在哪一层

### 如果是页面展示、交互或布局问题

优先改：

- `apps/desktop/src`

不要直接改：

- 量化执行逻辑
- OpenClaw 本体源码

### 如果是控制接口、状态模型、审计、mock 数据问题

优先改：

- `services/control-api`

### 如果是桌面壳、打包、窗口能力问题

优先改：

- `apps/desktop/src/main`
- `apps/desktop/src/preload.ts`
- `apps/desktop/package.json`

## 3. 当前 v1 的开发边界

### 允许做的事

- 完善桌面 UI
- 增加控制端页面能力
- 丰富本地控制服务和 mock 契约
- 增加 OpenClaw 编排相关接口
- 增强审计、历史记录、回测展示

### 暂时不要做的事

- 不要直接改 OpenClaw 源码
- 不要把 OpenClaw 变成直接交易执行者
- 不要默认引入 Web 端主流程
- 不要把网页登录入口改成 `bybit.com`

## 4. AI / OpenClaw 边界

后续无论是谁继续开发，都应保持下面的约束：

- OpenClaw 是编排执行层，不是交易执行层
- 最终交易仍由量化层直接调用 Bybit API
- 风控必须由量化层兜底
- 前端对 OpenClaw 的输入优先使用结构化任务

## 5. 新功能应该怎么加

### 新增控制动作

1. 先定义是否属于 `ChangeRequest` 或 `SchedulerCommand`
2. 在 `services/control-api/models.py` 中扩展模型
3. 在 `services/control-api/main.py` 中增加接口或行为
4. 在 `apps/desktop/src/api.ts` 中补请求函数
5. 在 `apps/desktop/src/App.tsx` 中接 UI

### 新增一个可视页面

1. 先确定它属于哪个导航模块
2. 优先复用已有数据查询和样式体系
3. 如果需要新的数据结构，先补 `docs/接口契约.md`
4. 再补后端模型和前端类型

### 新增真实量化内核对接

1. 先保持当前 API 契约不变
2. 用真实服务替换 `services/control-api/repository.py` 中的 mock 仓储
3. 审计事件模型尽量不要变

## 6. 提交前至少检查

- 前端能否正常构建
- 前端 lint 能否正常通过
- 控制服务能否正常启动
- 文档是否同步更新
- 新增交互是否符合“前端控制、量化执行、OpenClaw 编排”的边界

## 7. 测试后再交付

- 后续开发默认遵循“先实现、再测试、测试通过后再交付”。
- 不允许只完成代码改动就直接视为交付完成，必须补对应验证。
- 测试范围应跟随改动大小调整：
  - 小改动至少做构建、类型检查或启动验证
  - 接口改动至少做接口请求验证
  - 后端主链路改动优先补 `services/control-api/tests` 下的集成测试
  - 关键链路改动至少做端到端联调或回归验证
- 如果某项测试因为环境、凭证或第三方依赖无法执行，必须在交付说明中写清楚：
  - 未执行的测试项
  - 未执行原因
  - 对稳定性的潜在影响

## 8. 当前遗留事项

- 量化核心仍是 mock 控制服务，尚未接真实交易/回测引擎
- 当前手动交易只开放 Paper 路径，Demo / Live 还没有接真实执行引擎
- OpenClaw 当前主要是本地配置读取和健康探测占位，尚未接入真实的生产任务流
- Web 端尚未开始

## 9. 行情主图 / 策略活动回归护栏

`verify / smoke / report` 的详细口径、运行产物和历史基线只看 [docs/实施路线与接手清单.md#4-已验证命令](./实施路线与接手清单.md#4-已验证命令)。本节只保留容易误改的边界规则。

后续如果再改 `apps/desktop/src/App.tsx`、`apps/desktop/src/api.ts`、`services/control-api/main.py`、`services/control-api/bybit_public_client.py` 这一组行情链路，默认同时遵守下面几条，避免再次把“切币种 / 切周期”改慢、改错或改成空图：

- 总览页默认只保留市场主图这一条 SSE；`AI / ops / account / strategies` 的实时流只在各自专页开启，避免同源长连接占满浏览器请求槽位，拖慢 `/api/market/live`。
- `GET /api/market/live` 失败时，前端不能再喂 mock K 线，也不能把真实错误压成单纯 `HTTP 404 / 500`；必须透传后端 `detail`，方便定位“symbol 已失效”“当前自选中找不到该品种”等真实原因。
- `selectedSymbol` 的权威来源始终是后端真实 watchlist。若当前 symbol 不再存在于后端返回的 watchlist 中，前端必须自动纠正到第一个有效 symbol，不能继续拿旧缓存维持错图或空图。
- 主图渲染只允许使用当前 `symbol + timeframe` 对应的真实 `market-live` / `market` payload；其他币种或其他周期的缓存只能用于预取，不能直接拿来画当前主图。
- `/api/market/live` 在总览/行情页中默认采用“切换时一次请求 + 市场 SSE 持续刷新”；不要再叠加高频轮询，否则会和切换请求互相抢占浏览器连接槽位。
- 如果当前 `market-live` 返回空 candle 或失败，前端允许保留当前 key 的上一份有效真实图，但不能把别的 symbol / timeframe 的数据顶上来冒充当前图。
- 策略活动二级窗当前也会把区块行级语义指纹里的 `unknownActions / unknownBadges` 单独写进结构化摘要；只要仍有未映射动作或未映射标签，`semantic_bindings` 就不会被视为 `ok`。
- 策略活动二级窗的 `verify / smoke / report` 运行口径、产物和历史基线只看实施路线文档，不在这里重复展开。
