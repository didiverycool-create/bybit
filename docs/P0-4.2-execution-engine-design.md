# P0-4.2 统一执行引擎设计

**文档归属**: P0 主线缺口 §4.2 — “收口为统一的生产级执行引擎”
**生成日期**: 2026-04-26
**适用范围**: `services/control-api` 真实执行链路 + 策略运行时 + 手动交易入口
**前置阅读**: `docs/生产级真实量化交易系统剩余开发清单-2026-04-20.md` §4.2、`docs/架构总览.md`、`docs/接口契约.md` (`ExecutionPreview` / `OrderRecord` / `RiskDecision` 章节)

本设计文档只画蓝图，不引入任何代码改动。所有结构都基于当前 `main.py` / `repository.py` / `models.py` 已有事实，并明确标记 `TBD: needs prototyping` 的开放点。

## A. 目标与非目标

### A.1 目标

1. **单一执行路径**：把当前“`POST /api/trades/manual`(Paper 直接成交) / `POST /api/orders/exchange*`(真实委托) / `POST /api/strategies/{id}/execute`(手动策略执行) / 后台 `_auto_dispatch_strategy_signal_changes`(策略自动下发)” 这四条入口都收口到同一台状态机；Paper / Demo / Live 仅是状态机的尾部副作用差异。
2. **幂等可重试**：同一个 `(strategy_id, intent_seq, exchange_link_id)` 在网络重传、进程重启、UI 重复点击下，最多落地为一笔 `OrderRecord`。
3. **重启可恢复**：进程重启后能仅靠 `state.json` (短期) / SQLite (长期) + Bybit REST 快照 + 私有 WS 回放，重建当前所有 `ActiveExchangeOrder`，并继续状态机推进。
4. **检测外部干预**：用户在 Bybit 网页/App 直接撤单/改价时，系统必须在 60 秒内检测到 `EXTERNALLY_MODIFIED` 并把对应策略切回阻断态、补审计、停止后台再次自动补单。
5. **统一审计事件**：每一次状态迁移都映射到一条 `exchange_order.*` / `strategy.exchange_order.*` 审计事件，事件类型与现有审计家族保持兼容（避免桌面端时间线重写）。
6. **统一阻断口径**：任何拒绝执行都返回 `RiskDecision`（已存在），不再依赖 `blocked_reason` 子串解析。

### A.2 非目标

- 不在本期把回测 runner 收口进同一执行引擎（属于 §4.4 范围）。
- 不引入对 OpenClaw / AgentJob 的新依赖；`AgentJob` 仅消费引擎写出的审计事件。
- 不替换 Bybit REST / WebSocket 适配层 (`BybitPrivateClient` / `BybitPrivateRealtimeClient`) 的接口表面。
- 不重写 `RiskDecision` 风控判定 (P0-4.3)；本引擎只是 `RiskDecision` 的最大消费者。
- 不引入新的进程或 RPC 边界；引擎仍跑在 `services/control-api` 单进程中。

## B. 领域模型 (类型草图)

下列模型是“目标形态”，不是当前真实代码。`ExecutionIntent` 已在 `services/control-api/models.py:1560` 落地，本节标注扩展点；其余模型按现有 Pydantic / dataclass 风格描述。

### B.1 `ExecutionIntent` (扩展现有模型)

现状字段（`models.py:1560-1576`）：
```
strategy_id, strategy_name, source ("manual"|"auto"), mode, symbol, market,
side, quantity, price, signal, preview, decision, parameter_snapshot,
requested_by, note, created_at
```

本设计要补的扩展字段（仍是 `BaseModel`）：

```
intent_id: str               # ULID/UUID v7，跨重启稳定
intent_seq: int              # 同 strategy_id 单调递增；用于幂等去重
exchange_link_id: str        # 提交真实单时下发到 Bybit 的 orderLinkId；
                             # Paper 模式仍生成同一字段以保证日志统一
target_position: TargetPosition  # 见 B.2
parent_intent_id: Optional[str]  # 当本 intent 是 "amend" / "cancel-and-resubmit"
                                 # 的接续动作时，回填上一条 intent
ttl_seconds: int = 60        # 超时未 ACK 则强制走超时分支，详 §C
```

`source` 从现有的 `Literal["manual","auto"]` 扩展为 `Literal["manual","auto","recovery"]`，新增 `recovery` 用于冷启动重建场景（区别于真实用户 / 自动循环触发）。

### B.2 `TargetPosition`

代表“引擎认为该策略应当达到的仓位状态”。

```
class TargetPosition(BaseModel):
    strategy_id: str
    symbol: str
    market: Literal["spot", "perp"]
    side: Literal["flat", "long", "short"]
    size: Decimal                  # 已按 qtyStep 收敛
    reference_price: Decimal       # 决策瞬时参考价
    confidence: float              # 来自 StrategyRuntimeSnapshot.confidence
    derived_from: Literal["strategy_signal", "manual_intent", "stop_loss", "external_close"]
    decision_at: datetime
```

所有“目标 → 实际”差额（reuse / amend / submit / cancel）都从 `TargetPosition` + `current_position` 推导，而不是 `_dispatch_live_intent` 现状中“按预检里冻结的数量直接用”。这与 `_classify_live_order_reconciliation` (`main.py:7632`) 的 reuse / amend / submit 三分支保持等价但抽离出去。

### B.3 `ActiveExchangeOrder`

是对当前 `OrderRecord` (`models.py:1314`) 的薄包装，把 intent 链路和 reconciliation 状态显式化。

```
class ActiveExchangeOrder(BaseModel):
    order: OrderRecord            # 现有 source/origin/order_id/symbol/... 不动
    intent_id: Optional[str]      # 关联 ExecutionIntent.intent_id；
                                  # None 表示外部手动单 / 历史遗留单
    exchange_link_id: Optional[str]  # 即 orderLinkId
    state: ExecutionState         # 见 §C
    last_observed_at: datetime    # 最近一次从 WS / REST 看到该单的时间
    last_known_status: str        # Bybit 侧最近 orderStatus
    fills: list[FillFragment]     # 累计成交分片
    drift_detected: bool = False  # 检测到外部干预后置 True
```

`OrderRecord.source` 仍是 `Literal["mock","paper","bybit_private"]`。`ActiveExchangeOrder` 的存在不修改 `OrderRecord` 的 wire schema，桌面端无需变更。

### B.4 `ExecutionDecision`

是引擎接受 `(ExecutionIntent, current_state)` 后产出的“下一步动作”。**纯函数输出，无副作用**。

```
ExecutionVerb = Literal["keep", "amend", "cancel_and_resubmit", "cancel_only", "submit", "noop"]

class ExecutionDecision(BaseModel):
    verb: ExecutionVerb
    intent: ExecutionIntent
    target_order: Optional[ActiveExchangeOrder]   # 复用/改单/撤销针对哪一张
    stale_orders: list[ActiveExchangeOrder]       # 必须先撤掉的旧单
    new_order_request: Optional[NewOrderRequest]  # submit / cancel_and_resubmit 才有
    risk_decision: RiskDecision                   # 来自 evaluate_risk_decision
    reason_code: str                              # 直接复用 R59 reconciliation reason_code
    decided_at: datetime
```

注意：现状 `_classify_live_order_reconciliation` 已经返回 `LiveOrderReconciliation(action, reason_code, matching_order, stale_orders)`；`ExecutionDecision` 是它的超集，多了 `risk_decision` 字段、`cancel_only` (来自 `_cancel_strategy_exchange_orders`) 和 `noop` (来自 `StrategyExecutionNoopError`) 两个动作。

### B.5 `ExecutionResult`

引擎执行 `ExecutionDecision` 后的最终落地结果，包含审计链。

```
ExecutionResultStatus = Literal[
    "submitted",       # 真实单已发出
    "amended",         # 改单成功
    "reused",          # 复用已有单
    "cancelled",       # 仅撤单
    "noop",            # 目标已对齐，无需动作
    "blocked",         # RiskDecision.verdict == "block"
    "rejected",        # 交易所拒单
    "failed_transient", # 网络/超时类失败，可重试
    "externally_modified", # 检测到外部干预
]

class ExecutionResult(BaseModel):
    intent_id: str
    status: ExecutionResultStatus
    final_state: ExecutionState           # 见 §C
    order: Optional[ActiveExchangeOrder]
    audit_event_ids: list[str]            # 引擎写入的所有 ExecutionEvent.id
    risk_decision: RiskDecision
    error_detail: Optional[str]
    completed_at: datetime
```

`audit_event_ids` 是回放与排障的关键：任何 UI 卡片要解释“这一笔为什么走到 blocked”，只需按这组 id 拉对应 `ExecutionEvent` 即可，不再依赖前端临时拼装。

## C. 状态机

### C.1 状态集合

下面 9 个状态覆盖当前 `_dispatch_paper_intent` / `_dispatch_live_intent` / `_auto_dispatch_strategy_signal_changes` / `submit_exchange_order` / `replace_exchange_order` / `cancel_exchange_order` 的所有分支。

| 状态 | 含义 | 现状映射 |
| --- | --- | --- |
| `PROPOSED` | 已构建 `ExecutionIntent`，尚未做风控判定 | `_build_execution_intent_from_state` 之前 |
| `PREVIEWED` | 已生成 `ExecutionPreview` + `RiskDecision`；可允许或阻断 | 现 `evaluate_risk_decision` 后、`_dispatch_execution_intent` 前 |
| `ROUTED` | `ExecutionDecision` 已落定 (verb 已选)，但尚未发到 Bybit | 现 `_classify_live_order_reconciliation` 完成后 |
| `ACKED` | Bybit 已返回 `orderId`，本地已写入 `ActiveExchangeOrder` | 现 `private_data.create_order` 返回后 |
| `PARTIALLY_FILLED` | 已收到至少一片成交但未完全成交 | 现 `private_realtime` `execution` topic |
| `FILLED` | 完全成交 | 现 `_classify_exchange_order_status_event` 中 `Filled` |
| `CANCELED` | 已撤销（本地或交易所） | 现 `Cancelled` / `Cancelled_Stale` |
| `REJECTED` | 交易所拒单 | 现 `Rejected` (`exchange_order.rejected` 审计) |
| `EXTERNALLY_MODIFIED` | 外部干预后处于异常态 | 现没有对应状态；本设计新增 |

### C.2 转移表

下表的“触发事件”优先来自 Bybit 私有 WebSocket `order` / `execution` topic；REST 轮询是 fallback。

```
当前态           触发事件                          下一态                  副作用 / 审计事件
-------------    -----------------------------    ------------------     -------------------------------------
PROPOSED         build_execution_preview          PREVIEWED              （无；纯计算）
PREVIEWED        risk.allow + verb in {submit,    ROUTED                 emit "execution.routed"
                  amend, cancel_and_resubmit,
                  cancel_only}
PREVIEWED        risk.block                       (terminal: blocked)    emit "strategy.execution.blocked"
PREVIEWED        verb == "noop"                   (terminal: noop)       emit "auto.dispatch.noop"
ROUTED           bybit.create_order ok            ACKED                  emit "exchange_order.created"
ROUTED           bybit.amend_order ok             ACKED                  emit "exchange_order.replaced"
ROUTED           bybit.cancel ok                  CANCELED               emit "exchange_order.cancelled"
ROUTED           bybit.timeout / 5xx              (transient: failed_    emit "exchange_order.transient_failure"
                                                   transient → retry)    schedule retry with jittered backoff
ACKED            ws.order.partial_fill            PARTIALLY_FILLED       emit "exchange_order.partial_fill"
ACKED            ws.order.fill                    FILLED                 emit "exchange_order.filled"
ACKED            ws.order.cancel (own)            CANCELED               emit "exchange_order.cancelled"
ACKED            ws.order.cancel (external)       EXTERNALLY_MODIFIED    emit "exchange_order.external_cancel"
ACKED            ws.order.amend (external)        EXTERNALLY_MODIFIED    emit "exchange_order.external_amend"
ACKED            ws.order.reject                  REJECTED               emit "exchange_order.rejected"
ACKED            ttl_exceeded + still NEW         (transient: stale_     emit "strategy.exchange_order.
                                                   order)                 stalled" + alert (现已存在)
PARTIALLY_FILLED ws.order.fill                    FILLED                 emit "exchange_order.filled"
PARTIALLY_FILLED ws.order.cancel                  CANCELED               emit "exchange_order.cancelled"
EXTERNALLY_      operator ack                     (terminal: externally  emit "strategy.position_drift.
MODIFIED                                           _modified)             acknowledged"
```

“External” 与“own”的区分依据：本地 `ActiveExchangeOrder.intent_id` 必须存在，且最近一次 ROUTED → ACKED 时间戳与 WS 推送的 `updateTime` 不冲突。否则视为外部干预。详见 §E.3。

### C.3 状态机不变量

为后续 property-based 测试保留 (§G)：

1. 同一 `intent_id` 在引擎生命周期内最多产出一个 `ExecutionResult`（幂等）。
2. 任何状态都不能直接回到 `PROPOSED`；要重新提交必须新建 `ExecutionIntent` 并自增 `intent_seq`。
3. `FILLED` / `CANCELED` / `REJECTED` 是终态，不允许再发出 amend。
4. `EXTERNALLY_MODIFIED` 是终态，对应策略下一次自动循环必须先经过人工或自动 reconcile（写一条 `recovery` source 的新 intent）。
5. `ACKED → PARTIALLY_FILLED → FILLED` 的累计 `fills.size` 必须等于 `OrderRecord.qty`；不一致触发 `EXTERNALLY_MODIFIED`。

## D. 幂等性

### D.1 幂等键定义

```
idempotency_key = (strategy_id, intent_seq, exchange_link_id)
```

- `strategy_id`：自然主键。手动交易场景下使用伪策略 id（如 `manual:{operator_id}`），保证三元组仍唯一。
- `intent_seq`：同一 `strategy_id` 下的单调递增整数。引擎在 `_build_execution_intent_from_state` 入口处通过 SQLite 序列（详见 P0-5.1 设计）原子分配，避免并发请求冲突。
- `exchange_link_id`：等价于 Bybit `orderLinkId`。现状 `submit_exchange_order` 已经按 `strategy-{mode}-{strategy_id}-{uuid4().hex[:8]}` 生成，本设计要求引擎而不是 `submit_exchange_order` 拥有这个生成职责。

为什么是这三元组：

1. 仅用 `intent_id` 不够：客户端重试时新生成的 intent_id 会绕过去重；`intent_seq` 强制“同一逻辑请求不会有第二个 seq”。
2. 仅用 `exchange_link_id` 不够：Paper 模式下不会真实下单，没有 link_id；引入策略键和 seq 保证 Paper / Live / Demo 用同一去重原语。
3. 仅用 `strategy_id` 不够：同一策略可以连续提交多个 intent（如先 long 再 flat），需要 seq 区分。

### D.2 各状态下的去重规则

| 当前态 | 收到重复 intent 时 | 期望行为 |
| --- | --- | --- |
| `PROPOSED` / `PREVIEWED` | 直接返回已有 `ExecutionDecision`，不重新计算 risk | 重传不会触发额外的 Bybit instruments-info / 余额 RPC |
| `ROUTED` | 返回上一次 RPC 的 in-flight handle；若超时则按 §D.3 处理 | 不会发出第二份 `create_order` |
| `ACKED` | 返回当前 `ActiveExchangeOrder`，不发新 amend | 客户端拿到完全一致的 `ExecutionResult` |
| `PARTIALLY_FILLED` / `FILLED` / `CANCELED` / `REJECTED` | 返回已写入的终态 `ExecutionResult` | 不重复审计、不二次撤单 |
| `EXTERNALLY_MODIFIED` | 拒绝；要求客户端先确认外部干预（ack）再创建新 intent | 防止机器盲目对抗用户手动操作 |

### D.3 ACKED → FILLED 窗口期重试

这是最关键的边界。客户端在引擎已经 `create_order` 成功但本地还没收到 ACK 时重试，会引发“同一逻辑订单挂双单”。处理方式：

1. 在 `ROUTED` 状态登记 `pending_request{intent_id, exchange_link_id, started_at}`。
2. 重试到达时，引擎先查 `pending_request`，命中则**等待**（最长 `ttl_seconds`）原 RPC 完成，重用结果。
3. 若原 RPC 返回 5xx / 超时，引擎按 `exchange_link_id` 主动调用 Bybit `GET /v5/order/realtime` 探测：
   - 若 Bybit 已收到该 link_id → 用真实 `orderId` 推进到 `ACKED`，重试客户端拿到一致结果。
   - 若 Bybit 未收到 → 引擎重新发送一次 `create_order`，仍带原 `exchange_link_id`（Bybit 自身对 link_id 重复也会返回 `10001 duplicate`，按返回结果处理）。

> TBD: needs prototyping — Bybit 对同 `orderLinkId` 重复提交的实际错误码与可恢复性需要在 Demo 环境真测一次确认；当前 `submit_exchange_order` 没有走过这条路径。

## E. 恢复

### E.1 冷启动恢复

进程启动后，按下面顺序构建初始状态：

1. **本地权威**：从 SQLite (P0-5.1 落地后) / 当前 `state.json` 读取所有处于非终态的 `ActiveExchangeOrder` 与最近 7 天的 `ExecutionEvent`。
2. **交易所权威**：调用 `private_data.fetch_open_orders()` (REST) 拉一次完整未成交列表，与 `private_realtime.get_open_orders_snapshot()` 合并，去重以 `orderId` 为主键。
3. **三方对齐**：
   - 本地有、Bybit 也有 → 状态对齐为 `ACKED` / `PARTIALLY_FILLED`，刷新 `last_observed_at`。
   - 本地有、Bybit 没有 → 标记为 `EXTERNALLY_MODIFIED`（除非本地最后状态已是 `CANCELED` / `FILLED`，那种情况只是补 reconcile）。
   - 本地没有、Bybit 有 → 创建 `ActiveExchangeOrder(intent_id=None)`，标识为外部单或冷启动前未持久化的单；后续策略循环按 §F 规则决定接管或忽略。
4. **审计对账**：调用 `private_data.fetch_recent_trades(...)` 取最近 24 小时成交，把本地未关联的成交补写为 `recovery` source 的 `exchange_order.filled` 事件，避免空窗。

### E.2 WebSocket 重连后的增量对账

当前 `BybitPrivateRealtimeClient` 已经在断链后会触发重新订阅。增量对账算法：

1. 重连时记录 `reconnect_at`。
2. 等待首批 `order` / `execution` snapshot。
3. 对每个本地 `ActiveExchangeOrder`：
   - 若 snapshot 中有同 `orderId` → 比对 `qty / price / orderStatus`。差异写入 `EXTERNALLY_MODIFIED` 或正常推进。
   - 若 snapshot 中无该单 → 调用一次 REST `GET /v5/order/history?orderLinkId=...` 兜底确认最终状态（`Filled` / `Cancelled` / `Rejected`），按返回推进终态。
4. 清空“断链期堆积的本地动作”：在断链期间没有 ACK 的 ROUTED 状态强制走 §D.3 探测分支。

### E.3 外部干预检测

判定一笔状态变化是否“外部干预”，按以下规则按顺序判：

1. **本地无 intent**：`ActiveExchangeOrder.intent_id is None` → 永远算外部。
2. **`updateTime` 与 own action 不重叠**：
   - 引擎记录每次主动 `create / amend / cancel` 的 `(orderId, action, dispatched_at)` 到 in-memory `recent_actions` 环（保留最近 30 秒）。
   - 收到的 WS 推送若 `updateTime` 不命中任何 `recent_actions` 条目（容差 ±2 秒）→ 算外部。
3. **数量/价格不一致**：本地 `ActiveExchangeOrder.qty` 与 WS 报的 `qty` 不一致，但本地没有 amend 记录 → 算外部 amend。
4. **取消理由是 `UserCancel` 但本地无 cancel intent** → 算外部 cancel。

下游动作：

- 把策略对应的运行态切到 `guard_state="external_modified"`（沿用现有 `guard_state` 字段，不引入新字段）。
- 写入 `strategy.position_drift.detected` 审计事件（与现有 `strategy-position-drift:*` 系统提醒共用）。
- 暂停该策略的自动循环，直到 operator 在桌面端确认。

### E.4 冲突解决：Bybit 总是赢

当 `state.json` / SQLite 与 Bybit REST/WS 不一致时，**永远以 Bybit 为准**改写本地。但这次不一致本身要落审计，让排障可追溯。

实现位置：`AppRepository._reconcile_with_exchange()` 是新增方法（本期暂未实现，详 P0-5.1 §C 阶段 3）。每次写覆盖时同时插入：

```
event_type = "exchange_order.local_state_diverged"
payload = {
  "order_id", "local_state_before", "exchange_state",
  "diff_fields": [...], "resolution": "bybit_authoritative"
}
```

这样桌面端审计页能直接显示“N 月 N 日 X 笔状态被 Bybit 真实覆盖”，而不是悄悄修改。

> TBD: needs prototyping — 当 Bybit `GET /v5/order/history` 与 `GET /v5/order/realtime` 自身返回不一致（已知两个端点会有几秒延迟）时如何兜底，需要在 Demo 上实测一次确认。

## F. 迁移策略

按风险递增分四步落地。每一步都有独立 feature flag 开关，可在 `services/control-api/.runtime/state.json` 的 `settings.feature_flags` 字段中切换（feature_flags 字段需新增；TBD: needs prototyping — 字段位置可能放进 `SettingsPayload`）。

### F.1 Step 1: Shadow Mode

- 新增 `ExecutionEngine.compute_decision(intent)` 纯函数，返回 `ExecutionDecision`，**不执行任何副作用**。
- 现有 `_dispatch_execution_intent` 在调用旧路径前先调用 `compute_decision`，把结果写到 `audit_events[event_type="execution.shadow_decision"]`。
- 验证手段：跑现有 444 条集成测试，加 50 条新测试，确认 shadow decision 与旧路径产物一致（reuse / amend / submit / noop / blocked 五个口径）。
- Feature flag: `execution_engine.shadow=true`（默认开），生产场景可观察一周。

### F.2 Step 2: Paper 走新引擎

- 把 `_dispatch_paper_intent` 改成 `ExecutionEngine.execute(intent)` 的薄包装；Paper 模式不下交易所单，所以风险最低。
- Feature flag: `execution_engine.paper=true`。
- 桌面端无感知；`StrategyExecutionResult.kind="paper_trade"` 不变。
- 出问题时 flag 关掉立即回滚到 `repo.execute_strategy_signal()`。

### F.3 Step 3: Demo 走新引擎

- Demo 模式（`AccountMode.DEMO`）路径切到引擎。
- Demo 用的是 Bybit Demo 环境，资金风险为 0，是真实链路上的最佳灰度。
- Feature flag: `execution_engine.demo=true`。
- 验证手段：盯审计页 `exchange_order.created` / `exchange_order.filled` 与 Bybit Demo Web UI 完全一致；连续观察 7 天。

### F.4 Step 4: Live 走新引擎

- Live 模式切换。引擎此时已经在 Paper / Demo 上跑过两周。
- Feature flag: `execution_engine.live=true`。
- 同时打开“双写”一周：旧路径 disabled 但新引擎写完后仍把决策与 `_classify_live_order_reconciliation` 的预期值比对，差异落审计 `execution.engine_diff`。
- 双写期通过后移除旧的 `_dispatch_paper_intent` / `_dispatch_live_intent` 实体函数。

### F.5 回退预案

每个 step 的回退手段：

1. 关闭对应 flag，引擎降级回旧路径。
2. 若已有 `ActiveExchangeOrder` 处于 `ACKED` 但旧路径不识别其 `intent_id`，引擎留兼容字段 `legacy_order=true`，旧路径按 `OrderRecord.order_id` 直接读，不影响撤改。

## J. 开放问题

1. **ExecutionIntent 的 SQLite 落地时机** — 当前 intent 是临时对象，从未持久化。引擎要做幂等需要把 intent + intent_seq 落盘，但落盘点放在 `compute_decision` 之前还是 `execute` 之前？放前者增加噪音（被风控阻断的 intent 也要写），放后者的话客户端重试无法复用。倾向落在 `PROPOSED → PREVIEWED` 的转移上，需要 prototype 验证 SQLite 写入压力。

2. **`exchange_link_id` 重发策略** — Bybit 对同一 `orderLinkId` 是否允许第二次 `create_order`？文档说返回 `10001 duplicated linkId`，但实际行为需要在 Demo 环境真实试一次。如果不能复用，幂等键就必须退化成 `(strategy_id, intent_seq)` + 服务端去重 → 复杂度上升。

3. **手动交易的伪 strategy_id 命名** — 手动交易现状不挂 strategy；引入 `manual:{operator_id}` 后，桌面端 “最近活动” 面板要不要把这些手动 intent 单独分组？这影响 `StrategyActivitySnapshot` 的过滤规则。

4. **Recovery source 与现有 `ExecutionIntentSource` 的兼容** — 把 `Literal["manual","auto"]` 扩展为三元后，所有读 `intent.source` 的地方都要更新；可能涉及未列出的 audit / metrics 消费方。需要全仓 grep 确认。

5. **External modification 的 ack 流程** — 哪类用户能 ack？只允许 desktop_operator 还是允许 OpenClaw 自动 ack？后者会让“外部干预” 这个保护机制失效。倾向只允许人工 ack，需要确认。

6. **Demo 环境 Bybit instruments-info 与 Live 的差异** — 引擎依赖 `instruments-info` 校验 qtyStep / tickSize；如果 Demo 与 Live 上 instrument 元数据不同，灰度策略需要补一条“切 Live 时强制重拉 instruments-info”的步骤。
