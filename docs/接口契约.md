# 接口契约

本文档描述当前桌面控制端与本地控制服务之间的主要数据结构和接口语义，方便后续让 AI 或新线程继续开发时保持一致。

## 核心模型

### `ControlSnapshot`

首页控制总览的统一快照，包含：

- 资产指标
- 风险指标
- 策略指标
- AI 调度状态
- 告警摘要
- 待处理任务
- 当日表现
- `execution_health`

当前补充说明：

- `execution_health` 当前除了止损保护、冷却中、执行受阻、连续拒单、挂单停滞、仓位偏离外，也会带 `runtime_worker_running / runtime_worker_issue / runtime_last_error`
- `execution_health` 当前除 `top_issue` 外，也会带 `top_issue_strategy_id / top_issue_strategy_name / top_issue_symbol / top_issue_detail / top_issue_recommended_action`
- 若后台 `strategy runtime` 线程已经停止、但此前曾成功刷新过，`execution_health.top_issue` 当前也会提升为“运行线程未运行”
- 若后台 `strategy runtime` 线程长时间没有刷新成功，`execution_health` 当前也会带 `runtime_worker_stale / runtime_stale_seconds`
- 当后台 `strategy runtime` 线程异常或停止时，桌面端当前可调用 `POST /api/runtime/strategy-worker/restart` 发起恢复
- 当前也可调用 `GET /api/runtime/strategy-worker/status` 单独读取后台运行线程的健康状态与恢复建议
- 桌面端设置页与策略页当前优先消费这条独立接口，用于显示运行线程状态与恢复入口；`execution_health` 仍保留总览聚合语义
- 若 `POST /api/runtime/strategy-worker/restart` 恢复失败，当前会升成 `P1` 的 `system` 来源提醒“恢复运行线程失败”；后续成功恢复后会自动收起
- 线程异常或停滞当前也会生成 `system` 来源提醒，恢复后会自动收起并写入恢复审计事件
- `GET /api/control/snapshot` 的策略摘要首卡与 `GET /api/ops/live` 的 `execution_issue_total` 当前也会把这类运行线程问题计入统一执行健康

### `ChangeRequest`

前端任何“会改变系统状态”的操作，都先写成 `ChangeRequest`。

典型场景：

- 策略参数修改
- 策略启停
- 风控边界调整
- 提醒规则修改
- 回测发起
- AI 调度控制

状态流转：

- `draft`
- `queued`
- `running`
- `applied`
- `failed`
- `rolled_back`

### `AgentJob`

量化层或桌面端发送给 OpenClaw 的结构化任务。

关键字段：

- `job_type`
- `context`
- `allowed_actions`
- `timeout`
- `idempotency_key`
- `writeback_target`

当前补充说明：

- 当前本地 worker 会自动认领 `queued` 状态的 `AgentJob`
- 现已覆盖 `generate_daily_review`、`generate_backtest_review`、`reconcile_change_request`
- `idempotency_key` 已用于避免同一回测复盘被重复排队
- 外部直接 `POST /api/ai/jobs` 时，同一 `idempotency_key` 当前也会去重返回已有任务
- 失败或已取消的任务当前支持 `POST /api/ai/jobs/{job_id}/retry` 重新排队，新的任务会保留源任务关联和重试计数
- 高影响策略变更当前会自动排一条 `review_strategy_change` 任务，写回目标为 `strategy_activity`
- `review_strategy_change` 在完成或失败后，当前会额外写入 `strategy.change.review.completed / failed` 审计事件
- 当真实执行问题被升成 `system` 提醒时，当前也会自动排一条 `review_strategy_issue` 任务，写回目标同样为 `strategy_activity`
- `review_strategy_issue` 在完成或失败后，当前会额外写入 `strategy.issue.review.completed / failed` 审计事件
- 上述两类“跟踪完成”审计事件当前还会附带 `linked_review_id / linked_review_title / linked_review_period`
- 桌面端当前也会在系统日志/审计页直接复用这组 `linked_review_*` 元数据，支持从跟踪完成事件一键打开对应复盘结果
- 对通用 `openclaw.job.completed` 事件，桌面端当前也会兼容读取 `review_id / review_title / review_period`
- `AgentJob` 当前也会显式暴露 `strategy_id / linked_review_id / linked_review_title / linked_review_period / retried_from_job_id / retry_count`
- 桌面端当前也会在总览页与 `AI 调度` 页复用审计事件中的 `linked_review_id / review_id / strategy_id`，支持从实时 AI 事件流直接跳转
- `ReviewDocument` 当前也会显式暴露 `backtest_id`、`source_job_id / source_job_type / source_job_status`，便于从回测结果或复盘结果详情反向定位对应 AI 任务
- 对 `period=backtest` 的 `ReviewDocument`，当前还会继续暴露 `source_change_request_id / source_backtest_id / source_review_id / source_proposal_id / trigger_reason`，用于把回测来源链路一路保留到 `AI 复盘`、复盘详情和策略活动摘要
- `POST /api/strategies/{strategy_id}/review` 允许桌面端手动发起 `review_strategy_issue / review_strategy_change`，请求体包含 `review_kind / summary / detail / requested_by / request_key`，并会补写 `strategy.review.requested` 审计事件
- `review_strategy_change / review_strategy_issue` 在完成时，当前还会额外生成一条单策略 `ReviewDocument`，便于 `AI 复盘` 与策略活动二级窗直接复用
- 桌面端 `AI 复盘` 页当前会把 `period=strategy_issue|strategy_change` 的 `ReviewDocument` 单独归为“策略跟踪”，主复盘区只保留日报 / 回测复盘
- `GET /api/ai/reviews` 当前支持可选的 `strategy_id`、`backtest_id` 与 `period` 查询参数；`strategy_id` 会同时匹配 `review.strategy_id` 与提案关联的 `proposal.strategy_id`，`backtest_id` 则用于把单轮回测和对应回测复盘绑定起来
- 若策略活动或跟踪任务摘要当前带 `linked_review_id`，桌面端会优先用它直接聚焦对应复盘结果，而不是仅做页面切换
- 复盘任务当前优先接受结构化 JSON 结果：`summary`、`highlights`、`risks`、`proposals`
- 当 OpenClaw 返回结构化 `proposals` 时，会和本地启发式提案一起去重合并后写入 `ReviewDocument`
- 写入 `ReviewDocument` 时，当前还会自动把 `execution_health.top_issue / top_issue_detail / top_issue_recommended_action` 与运行线程问题补进 `risks`
- 当前发给 OpenClaw 的 `generate_daily_review / generate_backtest_review` 提示词，也会显式附带执行健康摘要与运行线程状态
- 这两类任务当前写入队列的 `context` 里，也会带 `execution_health / execution_top_issue / execution_top_issue_symbol / execution_top_issue_detail / runtime_worker_top_issue`
- 上述 `context` 当前还会带 `execution_top_issue_strategy_activity / review_strategy_activity`，把问题策略或当前复盘策略最近的运行态、提醒、委托、成交和审计事件压缩成摘要
- 对 `generate_backtest_review` 而言，`review_strategy_activity` 当前会在任务入队时直接固化；后续生成提示词和写回 `ReviewDocument` 时会优先复用这份上下文，不再因稀疏上下文临时回拉 Bybit 实时链路。仅 `generate_daily_review` 仍保留最新执行健康兜底
- `review_strategy_activity` 当前也会继续固化 `latest_backtest / latest_backtest_review / latest_backtest_job / recent_backtests`，让任务快照能直接看到最近回测，以及最近回测已经落到结果还是仍停在回测复盘任务里
- `review_strategy_activity` 当前也会继续固化 `latest_audit_event / recent_audit_events` 的高价值摘要，并补齐结构化的 `latest_audit_event_record`；审计字符串会优先写入 `summary / result_summary / impact / manual_followup`，不再只保留 `event_type · source`
- `review_strategy_activity` 当前也会继续固化 `latest_alert / latest_order / latest_trade`，并补齐结构化的 `latest_alert_record / latest_order_record / latest_trade_record`；同时还会继续固化 `latest_pending_alert / latest_pending_alert_record`、`latest_active_order / latest_active_order_record` 与 `latest_historical_order / latest_historical_order_record`，分别指出“当前仍待处理的提醒”“当前仍可操作的活动委托”和“历史委托里最新的一张”。其中 `recent_orders / recent_trades / recent_alerts / recent_audit_events` 会先按时间倒序归一化，`latest_order*` 会优先在“最新活动委托”和“最新历史委托”之间选取创建时间更新的一条，而 `latest_active_order*` 会始终锁定活动态里最新的一条，`latest_historical_order*` 会始终锁定历史委托里最新的一条，`latest_alert*` 会按真实时间挑最新，`latest_pending_alert*` 会始终锁定未确认提醒里最新的一条，`latest_trade*` 也会按真实时间挑最新，让任务快照在列表外既不会漏掉最近一笔委托，也不会漏掉当前仍可改单/撤单的那张活动单，还能直接拿到当前待处理提醒和当前最新历史委托
- `review_strategy_activity` 当前也会继续固化 `latest_proposal / latest_change_request`，让任务快照在最近列表外还能直接拿到最近提案与最近变更的近场摘要
- `review_strategy_activity` 当前也会继续固化 `latest_proposal_change_request / latest_proposal_backtest / latest_proposal_review / latest_proposal_job`，以及对应的 `latest_actionable_proposal_*`，让任务快照能直接知道最近提案和当前可处理提案已经落到哪一层
- `review_strategy_activity` 当前也会继续固化 `latest_proposal_backtest_record / latest_proposal_review_record / latest_proposal_job_record`，以及对应的 `latest_actionable_proposal_*_record`，让任务快照在这些结果或任务不在全局列表时，仍能直接拿到完整 `BacktestRun / ReviewDocument / AgentJob`
- `review_strategy_activity` 当前也会继续固化 `latest_actionable_proposal / latest_actionable_change_request / latest_actionable_backtest / latest_actionable_backtest_review / latest_actionable_backtest_job / latest_actionable_primary_review / latest_retryable_tracking_job`，显式指出当前仍可处理的提案、仍可重试/重跑的变更、当前仍可继续处理的回测/复盘，以及仍可重试的跟踪任务
- `review_strategy_activity` 当前也会继续固化 `latest_change_request_backtest_record / latest_change_request_review_record / latest_change_request_job_record`，以及对应的 `latest_actionable_change_request_*_record`，让任务快照在这些结果或任务不在全局列表时，仍能直接拿到完整 `BacktestRun / ReviewDocument / AgentJob`
- `review_strategy_activity` 当前也会继续固化 `latest_change_request_source_backtest_record / latest_change_request_source_review_record / latest_change_request_source_proposal_record`，以及对应的 `latest_actionable_change_request_source_*_record`，让任务快照在这些来源对象不在全局列表时，仍能直接拿到完整 `BacktestRun / ReviewDocument / StrategyProposal`
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_audit_event / latest_alert / latest_order / latest_trade`，并补齐结构化的 `latest_audit_event_record / latest_alert_record / latest_order_record / latest_trade_record`；同时还会继续返回 `latest_pending_alert / latest_pending_alert_record`、`latest_active_order / latest_active_order_record` 与 `latest_historical_order / latest_historical_order_record`，显式告诉桌面端“当前待处理提醒”“当前活跃委托”和“当前最新历史委托”分别是哪一张。其中 `recent_orders / recent_trades / recent_alerts / recent_audit_events` 也会先按时间倒序归一化，`latest_order*` 同样会优先在“最新活动委托”和“最新历史委托”之间选取更新的一条，而 `latest_active_order*` 会始终锁定活动态里最新的一条，`latest_historical_order*` 会始终锁定历史委托里最新的一条，`latest_alert*` 会按真实时间挑最新，`latest_pending_alert*` 会始终锁定未确认提醒里最新的一条，`latest_trade*` 也会按真实时间挑最新，供桌面端策略活动面板顶部同时复用最近一条提醒、当前待处理提醒、最近一条委托、当前活跃委托和当前最新历史委托，而不必再只从最近列表第一条做本地推断
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_proposal / latest_change_request`，供桌面端策略活动面板顶部直接显示最近提案与最近变更摘要，而不必再只从最近列表第一条做本地推断
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_proposal_change_request / latest_proposal_backtest / latest_proposal_review / latest_proposal_job`，以及对应的 `latest_actionable_proposal_*`，供桌面端直接锁定最近提案和当前可处理提案已经落到的变更、回测、复盘或任务
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_proposal_backtest_record / latest_proposal_review_record / latest_proposal_job_record`，以及对应的 `latest_actionable_proposal_*_record`，供桌面端在这些结果或任务暂时不在全局列表时，仍能直接复用完整对象继续打开结果链
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_actionable_proposal / latest_actionable_change_request / latest_actionable_backtest / latest_actionable_backtest_review / latest_actionable_backtest_job / latest_actionable_primary_review / latest_retryable_tracking_job`，供桌面端直接复用“当前可处理提案 / 当前可处理变更 / 当前可处理回测 / 当前可处理复盘 / 当前可重试任务”这组近场动作，而不必长期只从最近列表本地推断
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_change_request_backtest_record / latest_change_request_review_record / latest_change_request_job_record`，以及对应的 `latest_actionable_change_request_*_record`，供桌面端在这些结果或任务暂时不在全局列表时，仍能直接复用完整对象继续打开最近变更和当前可处理变更的结果链
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_change_request_source_backtest_record / latest_change_request_source_review_record / latest_change_request_source_proposal_record`，以及对应的 `latest_actionable_change_request_source_*_record`，供桌面端在来源对象暂时不在全局列表时，仍能直接复用完整对象继续打开最近变更和当前可处理变更的来源链
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_backtest_record / latest_actionable_backtest_record`，供桌面端直接复用完整 `BacktestRun` 细节来展示最近回测/当前可处理回测的门禁、窗口、来源链与重跑动作，而不必长期只靠全量回测列表本地查表
- `GET /api/strategies/{strategy_id}/activity` 当前也会继续返回 `latest_backtest_review_record / latest_backtest_job_record / latest_actionable_backtest_review_record / latest_actionable_backtest_job_record / latest_primary_review_record / latest_actionable_primary_review_record / latest_tracking_review_record / latest_tracking_job_record / latest_retryable_tracking_job_record`，供桌面端和 `review_strategy_activity` 直接复用完整 `ReviewDocument / AgentJob` 结构来打开结果、任务和来源链，而不必长期只靠全局 `reviewCatalog / scheduler.jobs` 本地兜底

### `SchedulerCommand`

AI 调度硬控制指令，固定支持：

- `pause`
- `resume`
- `cancel_job`
- `cancel_all`
- `freeze_publish`
- `enter_manual_override`

### `BacktestRun`

回测任务记录，统一保存：

- 策略版本
- 品种范围
- 时间范围
- 数据粒度
- 手续费模型
- 滑点模型
- 参数快照
- 收益率、回撤、胜率、成交统计
- `reference_only`
  表示本次回测区间是否未命中真实入场信号、只能按基础价格路径生成参考权益曲线；若为 `true`，`trades / win_rate` 应视作“无真实成交样本”
- `sample_quality`
  统一的样本质量标记，当前固定为 `reference_only | low_sample | sufficient`
- `requested_range_start / requested_range_end`
  回测请求窗口元数据：把原始 `data_range` 在回测创建时解析成绝对起止时间，便于相对区间在后续 AI 复盘、桌面端和人工排查中保持稳定语义
- `retrieved_window_completion_pct / used_window_completion_pct`
  回测窗口覆盖率元数据：分别表示“实际取样窗口”和“最终回测窗口”相对目标请求窗口的覆盖百分比
- `history_source`
  回测样本来源：当前固定为 `exchange_history | market_detail_fallback`，分别表示“来自交易所历史 K 线 / 已回退到工作台行情快照样本”
- `history_source_reason / history_source_detail`
  当 `history_source=market_detail_fallback` 时，额外说明这次回退的原因与细节；当前原因固定为 `none | exchange_fetch_failed | insufficient_exchange_samples`
- `history_source_recommended_data_range / history_source_recommended_timeframe / history_source_recommended_action`
  当 `history_source=market_detail_fallback` 时，结构化给出下一步建议：是“先恢复历史拉取后按原参数重跑”，还是“先改用建议区间/周期补样本”
- `decision_readiness / decision_readiness_detail / decision_recommended_data_range / decision_recommended_timeframe / decision_readiness_action`
  回测结果的统一结论门禁：当前固定为 `ready | sample_incomplete | research_only`，分别表示“可继续判断 / 样本仍待补 / 仅供研究参考”；其中 `decision_recommended_*` 会结构化给出“按建议重跑”的目标区间与周期
- `source_change_request_id / source_backtest_id / source_review_id / source_proposal_id / trigger_reason`
  回测来源链路元数据：用于标记这轮回测是“手动创建 / 由哪条变更触发 / 门禁重跑 / 复盘建议重跑 / 接受提案”中的哪一种，以及它直接继承自哪条变更、哪轮回测、哪条复盘或哪条提案
- `requested_candle_estimate / requested_candle_limit / retrieved_candle_count / used_candle_count / history_truncated`
  回测样本窗口元数据：分别表示目标区间理论需要的 K 线根数、当前回测样本上限、实际取到的根数、实际参与本地回测的根数，以及是否因当前回测样本上限或本地窗口上限发生截断
- `history_gap_reason`
  回测样本缺口原因：当前固定为 `none | sample_cap | insufficient_history`，分别表示“无缺口 / 被当前回测样本上限截断 / 交易所当前可用历史本身不足”
- `retrieved_range_start / retrieved_range_end / used_range_start / used_range_end`
  回测样本时间范围元数据：分别表示本次实际取到的历史样本起止时间，以及最终参与本地回测的窗口起止时间
- `full_window_recommended_data_range / full_window_recommended_timeframe / full_window_recommended_action`
  当 `history_truncated=true` 时给出的结构化补样本建议：分别表示建议补样本时应使用的区间、周期，以及直接面向桌面端/UI 的下一步动作说明

### `WorkspacePreferences`

桌面控制端的工作台状态快照，当前用于保存：

- 默认页面
- 布局方案
- 当前模式
- 当前品种
- 当前行情周期
- 当前策略
- 当前聚焦回测
- 策略页当前打开的活动/跟踪二级面板
- 策略页当前编辑器草稿所属策略，以及未保存的参数/风险预算草稿
- 当前打开的复盘结果详情小窗
- 当前聚焦的 AI 调度任务
- 当前聚焦的 replay review
- 当前定位的提案
- 当前定位的 `ChangeRequest`
- 回测页筛选与复盘跟踪范围
- 提醒/成交/审计筛选器
- 审计搜索词
- 总览卡片顺序
- 总览卡片显隐
- 最近保存时间

若 `selected_change_request_id` 在恢复时已不属于当前策略，桌面端会自动切回这条变更所属策略，再恢复“当前定位变更”详情；若 `selected_proposal_id` 仍有效，也会按提案所属策略恢复策略页上下文；若 `selected_scheduler_job_id` 仍有效且该任务带明确 `strategy_id` 或任务上下文可推导策略，则会按这条 AI 调度任务恢复调度页上下文；若 `selected_review_inspector_id` 仍有效，则会自动重开复盘结果详情小窗；若同时保留了 `selected_review_inspector_strategy_id`，则会优先用这条策略语境恢复小窗来源信息，并同步把策略与主品种切回同一上下文；若 `selected_review_id` 仍有效且该 review 带明确 `strategy_id`，则会按这条 replay review 恢复回放页上下文。
若 `selected_symbol / selected_strategy_id / selected_backtest_id / selected_scheduler_job_id / selected_review_inspector_id / selected_review_id / selected_proposal_id / selected_change_request_id` 已经不再存在，控制端会在返回 `WorkspacePreferences` 前自动清理这些陈旧引用，避免旧定位状态重复恢复。
若 `active_section=strategy` 且 `selected_change_request_id` 仍有效，控制端会优先按这条变更对齐 `selected_strategy_id`；若没有有效变更但 `selected_proposal_id` 仍有效，则会继续按该提案对齐策略与主品种；若 `active_section=scheduler` 且 `selected_scheduler_job_id` 仍有效，则会优先按该 AI 调度任务对齐策略与主品种；若 `active_section=replay` 且 `selected_review_id` 仍有效，则会优先按该 review 对齐策略与主品种；若 `active_section=backtest` 且 `selected_backtest_id` 仍有效，则会优先按该回测对齐策略焦点。
上述两类恢复当前也会继续对齐 `selected_symbol`，优先切到对应策略或回测的主品种。
若 `active_section=strategy`，还可继续保存 `selected_strategy_detail_panel` 以及 `selected_strategy_tracking_kind / summary / detail`；桌面端恢复策略页时会据此重开活动或跟踪面板。若策略编辑器当前已经产生未保存草稿，控制端也会继续保留 `selected_strategy_editor_strategy_id / selected_strategy_editor_parameter_drafts / selected_strategy_editor_risk_budget_draft`，允许在同一策略页内切到活动/跟踪后再返回编辑器时继续恢复；若本次恢复时编辑器本身就是打开的，且 `selected_strategy_editor_strategy_id` 仍有效，控制端也会优先按这条草稿所属策略恢复策略焦点；若当前模块已不在策略页，或草稿所属策略与当前策略焦点不再一致，控制端会在返回 `WorkspacePreferences` 前自动清理这组字段，避免恢复出越界或串策略的编辑器状态。

补充说明：

- `GET /api/strategies/live` 当前会基于最新行情生成最小策略运行态，优先服务桌面端策略页和后续运行看板
- 当前已覆盖趋势、均值回归、突破三类本地启发式运行评估
- 当 `paper` / `paper_only` 策略的运行信号从 `flat/watch` 切换到 `long/short`，或从持仓信号回到 `flat` 时，会自动补一笔 `origin=strategy` 的纸面成交

- `GET /api/strategies/live` 当前会附带 `execution_preview`，用于说明当前信号若继续按 `paper` 执行，会如何影响仓位和可用余额
- 当工作台当前模式切到 `live/demo` 且策略模式匹配时，`GET /api/strategies/live` 现在也会直接附带对应的真实顾问式执行预检；若该模式下当前不可执行，则会返回阻断原因
- 当 `live/demo` 策略的真实顾问式预检因为余额不足、现货可卖数量不足或交易所约束不满足而被拦住时，`GET /api/strategies/live` 当前也会把该策略运行态标成 `guard_state=auto_dispatch_blocked`，并把预检里的 `blocked_reason / recommended_action` 一并带回
- 即使当前工作台 `selected_mode` 不在该策略的真实模式上，只要最近一次真实自动执行已经被拦住，`GET /api/strategies/live` 当前也会优先把最近一次阻断明细回填到 `guard_detail / note / next_action`，避免只看到泛化的“自动执行被系统拦截”
- `strategy-auto-dispatch:*` 系统提醒与 `execution_health.top_issue_recommended_action` 当前也会尽量按阻断明细给出具体建议，例如补 `UNIFIED / CONTRACT` 等当前私有账户桶位余额、撤销现货卖单占用或先恢复私有/公共实时链路，而不是固定模板
- 当后台自动执行直接命中真实预检阻断时，原始 `recommended_action` 当前也会继续沿着“自动执行阻断提醒 -> 审计事件 -> 运行态回填 -> 控制总览”保留下来，避免中途退回到只靠文案反推
- 后台 `strategy runtime` 循环当前会在 `running + live/demo` 策略信号切换后自动提交或复用真实策略委托
- 若当前真实策略委托的方向、数量、价格已经与最新信号一致，后台循环与手动执行都会直接复用该委托，不再触发无意义改单
- 若 `live/demo` 策略配置了 `stop_loss_pct` 且当前真实仓位触发阈值，后台循环会自动撤掉遗留策略委托、升成 `P0` 系统提醒，并让策略级执行预检直接返回阻断原因
- 当真实策略进入 `shadow / paused / watch` 等非执行状态时，后台循环会自动清理该策略遗留的真实委托
- `GET /api/strategies/stream` 会以 `text/event-stream` 形式持续推送 `StrategyLiveSnapshot`
- `GET /api/strategies/{strategy_id}/execution-preview` 当前会按工作台模式返回策略级执行预检：
  - `paper`：沿用当前策略运行态里的目标仓位差额预检
  - `demo/live`：按当前策略信号方向和估算手数，返回 Bybit 私有账户顾问式预检
  - 对 `demo/live` 而言，当前会先按 `Bybit 私有账户可用余额 × 策略 risk_budget` 收敛可新增仓位，再叠加可复用的现有仓位/旧单释放占用，并按 `instruments-info` 的 `qtyStep / tickSize` 收敛到交易所精度，统一生成 `execution preview`、自动执行委托和 `target_position_size`；若余额联动后的目标仍低于最小下单门槛，会直接返回显式阻断而不是继续按旧的固定手数预检

  - 若当前同一策略在同品种上已有未成交、且后续会被复用、改单或撤销的可释放占用委托，这部分余额或保证金占用当前也会同步释放回策略级 sizing 与真实预检，避免被自己的旧单误判成余额不足

- 同一自选提醒规则在冷却时间内即使已经被确认，也不会再次生成重复的市场提醒，直到冷却窗口结束
- `GET /api/account/live` 会把账户总览、持仓、未成交委托和历史订单统一打包返回，供交易记录页和首页辅助区域做同源联动

- `GET /api/account/*` 在未配置 Bybit 私有 API Key 且当前模式为 `paper` 时，会根据本地 Paper 成交动态派生账户总览、持仓和余额，而不是返回固定 mock 账户
- `GET /api/account/order-history` 在未配置 Bybit 私有 API Key 且当前模式为 `paper` 时，会根据本地 Paper 成交派生历史订单记录

- `POST /api/account/paper/orders/cancel-all` 当前只允许在 `paper` 模式调用，会批量取消当前全部本地未成交委托，并把结果写入历史订单与审计事件
- `POST /api/account/paper/orders/{order_id}/replace` 当前只允许在 `paper` 模式调用，会基于“排除当前委托自身冻结量”的风控结果完成改价改量
- `POST /api/account/paper/orders/{order_id}/cancel` 当前也只允许在 `paper` 模式调用，会把未成交委托移入历史订单并释放冻结量
- `POST /api/orders/exchange` 当前会把桌面端的 `demo / live` 手动交易请求转换成 Bybit 真实限价委托，并返回统一的 `OrderRecord`

- `POST /api/orders/exchange/{order_id}/replace` 当前会在 `demo / live` 模式下直接修改真实未成交委托，并同步刷新私有实时缓存
- `POST /api/orders/exchange/{order_id}/cancel` 当前会撤销当前模式下的真实未成交委托，并立即从私有实时缓存中移除
- `POST /api/orders/exchange/cancel-all` 当前会按当前模式批量撤销全部真实未成交委托，并立即清空私有实时缓存中的未成交列表；若原委托来自策略，历史订单里的 `origin` / `strategy_id` 仍会保留
- `POST /api/account/exchange/positions/{symbol}/close` 当前会根据真实持仓方向自动生成单笔平仓限价委托；永续仓位会附带 `reduceOnly`；`spot` 持仓则要求该币种当前可用数量足以覆盖整笔平仓，否则会阻断并提示先撤销相关挂单；若同一 `symbol` 同时存在 `spot` / `perp` 多市场持仓，也会先阻断，避免误平错误市场
- `POST /api/account/exchange/positions/close-all` 当前会先对全部真实持仓做整批预检；只要其中任一持仓当前不可安全平仓，就会整批阻断，不会先提交部分平仓单

- `GET /api/account/*` 在未配置 Bybit 私有 API Key 且当前模式不是 `paper` 时，仍会稳定回退到 mock 数据
- `GET /api/account/*` 在当前模式为 `paper` 时，会优先返回本地 Paper 账户；即使本机已经配置 Bybit 私有 Key，也不会把 `paper` 视图切到真实只读账户
- `GET /api/account/overview`、`GET /api/account/live`、`GET /api/account/positions`、`GET /api/account/orders`、`GET /api/account/order-history` 当前也支持可选 `mode=paper|demo|live` 查询参数，用于在不改工作台 `selected_mode` 的前提下直接诊断另一套账户视图；未传时仍按当前工作台模式返回
- `GET /api/account/*` 在已配置私有 Key 且真实账户为空时，会返回真实空结果，不再错误回退到 mock 持仓或 mock 委托
- `GET /api/account/positions` 在 `demo / live` 下当前除读取 Bybit `position/list` 外，也会用钱包 `coin[]` 自动补出 `spot` 持仓；若同一现货仓位同时在两处出现，会优先保留显式持仓记录并自动去重
- `GET /api/trades` 在已配置 Bybit 私有 Key 时，会优先读取 Bybit 私有最近成交历史，并与本地 Paper / 策略成交记录按时间合并返回
- 当真实成交命中本地 `private_order_metadata`，或其 `orderLinkId` 使用新的 `strategy-{mode}-{strategy_id}-...` 形式时，`GET /api/trades` 现在会把该笔成交还原成 `manual / strategy` 来源，并在可推断时附带真实 `strategy_id`
- `POST /api/trades/preview` 当前会返回统一执行预检结果，供桌面端在真正提交前展示名义价值、可用余额变化、持仓变化和阻断原因
- `ExecutionPreview` 当前也会在可推断时返回 `recommended_action`，用于给桌面端展示“下一步该怎么做”，避免只给一段阻断文案
- `POST /api/trades/preview` 在 `demo / live` 模式下，当前还会优先读取 Bybit `instruments-info` 做本地下单校验，先检查最小下单量、数量步长、价格步长和最小名义价值，再决定是否允许真实提交
- 若 `demo / live` 顾问式预检因为 Bybit 可用余额 / 保证金不足被拦住，`blocked_reason` 当前会直接带出“当前可用余额”和“本次委托约需名义价值”，方便区分账户资金不足与参数错误
- `POST /api/trades/preview` 与 `POST /api/trades/manual` 当前共享同一套 `paper` 风控判断，因此预检里的阻断原因应与真正提交失败时保持一致
- `POST /api/trades/preview` 在 `demo / live` 模式下会返回顾问式真实预检，基于 Bybit 私有账户余额、持仓和模式匹配情况给出阻断原因或仓位影响
- `POST /api/trades/preview` 在 `demo / live` 的 `spot sell` 场景下，当前会优先按钱包返回的该币种可用数量做门禁；若缺少该字段，再回退到“总持仓 - 同品种未成交卖单占用”；`exclude_order_id` 仍可用于改单时排除当前委托自身占用

- `GET /api/integrations/bybit-private` 当前也会返回 `config_path / config_exists / example_config_path`，用于设置页和人工排查直接定位本机只读 Key 配置入口

## 约束规则

### 交易执行

- 手动交易和自动交易都必须由量化层完成
- OpenClaw 不直接执行交易
- 风控必须在量化层生效
- 当前 `POST /api/trades/manual` 仍只负责 `paper` 模式的直接成交写入；`demo/live` 手动委托已经走 `POST /api/orders/exchange`，真实委托的改单 / 撤单 / 全撤也已有独立接口

### Bybit 域名

- 网页端入口固定使用 `https://www.bybit-global.com/`
- API 接口域名与网页端入口分离
- 账户、持仓、委托等私有数据必须通过 Bybit 私有 API + API Key 访问，不能直接复用网页登录态

### 前端与 OpenClaw 的关系

- 前端不直接给 OpenClaw 自然语言大指令作为唯一依据
- 前端应该优先发送结构化任务
- OpenClaw 主要消费 `ChangeRequest` 和 `AgentJob`

### 工作台状态同步

- 工作台状态先保存在桌面本地缓存
- 服务在线时再同步到 `WorkspacePreferences`
- 当前会一起保存：
  - 主页面、布局 preset、当前账户模式、主盯盘品种、主图 K 线周期
  - 当前策略、当前聚焦回测、回测页 `仅当前策略/全策略` 筛选
  - 复盘跟踪范围
  - 提醒页严重级别/状态/范围筛选
  - 成交页模式/来源/范围筛选
  - 审计页严重级别/来源/范围筛选与搜索词
  - 总览卡片顺序、显示状态、折叠状态
- 这样既保证本机重开可恢复，也方便后续 AI / 新线程读取当前控制端习惯

## 后续扩展建议

如果后续要替换 mock 服务为真实量化核心，优先保持这些接口路径和数据模型不变，让桌面端保持最小改动。
