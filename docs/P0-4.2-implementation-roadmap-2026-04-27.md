### A.1 Bybit Demo `orderLinkId` 复用真测 (J.2 拍板硬约束)

**目标**：确认 `(strategy_id, intent_seq, exchange_link_id)` 幂等三元组的最后一个分量在 Bybit 侧的真实行为。设计在 `docs/P0-4.2-execution-engine-design.md` §D.3 假设 Bybit 接受同 `orderLinkId` 的第二次提交（idempotent return），但 J.2 决策明确"先按假设设计；wave-3 启动前必须实测"。

**实测脚本（不写入仓库，临时一次性）**：
- 用 `services/control-api/exchange/bybit_private.py` 现成的 `BybitPrivateClient.create_order`（`main.py:4882` 已经在用）。
- 启动一份 Demo 模式的 control-api（`services/control-api/.env.demo` 把 `BYBIT_PRIVATE_BASE_URL` 指向 `https://api-demo.bybit.com`）。
- 用 `curl` 或 `httpx` 直接 POST `/v5/order/create`，`orderLinkId="probe-{ULID}"`，`category="linear"`，`symbol="BTCUSDT"`，`side="Buy"`，`qty=0.001`，`price=10000`（远低于市价以避免成交），`timeInForce="GTC"`。

**期望响应形态**：

第一次（成功）：
```
{"retCode": 0, "result": {"orderId": "...", "orderLinkId": "probe-..."}, ...}
```

第二次（同 `orderLinkId` 重发，5 秒内）：
- 如果返回 `retCode=0` 且 `orderId` 与第一次相同 → idempotent return → 设计成立，§D.3 走"探测 + 复用"分支。
- 如果返回 `retCode=10001`（duplicate）且响应不带 `orderId` → 设计需要降级。
- 如果返回任何其他错误码 → 暂停 wave-3，请求 user 决策。

**记录位置**：把实测响应原文（脱敏后）追加到本文件 §I.1 附录或新建 `docs/P0-4.2-bybit-orderlinkid-probe-2026-04-XX.md`。

**WS 配套**：在第一次 `create_order` 后立即订阅 `private_realtime` 的 `order` topic，记录 `orderId / orderLinkId / orderStatus / updateTime` 的推送时序。这一段数据用于 §C.3 外部干预检测的 `recent_actions` 容差校准（设计稿里写的是 ±2 秒，实测可能要调）。

**通过线**：
- [ ] 实测响应 JSON 已记录
- [ ] 行为符合"idempotent return"或已在备用方案文档中标注
- [ ] WS `updateTime` 与 REST `dispatched_at` 的时差中位数 < 2 秒

### B.1 `services/control-api/execution_engine.py`

```python
"""Round 124+ — Unified ExecutionEngine for P0-4.2.

Coordinator that owns the (compute_decision → execute → recover) pipeline. See
docs/P0-4.2-execution-engine-design.md §B-§E for the contract; this module is
the single owner of every Bybit RPC dispatch path (paper / demo / live).
"""

from __future__ import annotations

from dataclasses import dataclass
from typing import Optional

from models import (
    ActiveExchangeOrder,
    ExecutionDecision,
    ExecutionIntent,
    ExecutionResult,
    RecoveryReport,
)


class ExecutionEngine:
    __slots__ = ("_repo", "_persistence", "_risk_engine", "_clock")

    def __init__(
        self,
        repo,                    # services.control-api.repository.AppRepository
        persistence,             # services.control-api.persistence.PersistenceUnit
        risk_engine,             # services.control-api.risk_engine.RiskEngine
        clock=None,
    ) -> None: ...

    def compute_decision(
        self,
        intent: ExecutionIntent,
        state,                   # AppState snapshot
    ) -> ExecutionDecision: ...

    def execute(
        self,
        decision: ExecutionDecision,
    ) -> ExecutionResult: ...

    def recover(
        self,
        state,                   # AppState
        exchange_state,          # OpenOrderSnapshot from BybitPrivate
    ) -> RecoveryReport: ...
```

依赖说明：
- `compute_decision` 是纯函数（不写 SQLite，只读 state）。
- `execute` 内部按 `decision.verb` 路由到 `_apply_paper` / `_apply_live` / `_apply_amend` / `_apply_cancel` / `_apply_noop`（私有方法，签名延后到实现期定）。所有 SQLite 写入必须在 `with PersistenceUnit() as unit:` 上下文里完成。
- `recover` 走 P0-4.2 §E.1 三方对齐，返回 `RecoveryReport(active_orders, divergences, recovered_intents)`。

## F. 风险登记 (Risk register)

按 step 列出"会出什么问题 / 怎么发现 / 如何回滚"。括号内是风险等级（H/M/L）。

### F.1 Shadow

- **R-F1-1 (M)**：`compute_decision` 与旧 `_classify_live_order_reconciliation` 在 reuse / amend / submit 三分支上行为分歧，导致 `execution.shadow_decision_diverged` 持续告警，但用户无感知（旧路径仍跑）。**发现**：Prometheus `bybit_control_execution_engine_decisions_total{result="diverged"}` 持续 > 1/h；audit `execution.shadow_decision_diverged` 24h 计数 > 100。**回滚**：关 `execution_engine.shadow` flag。
- **R-F1-2 (L)**：`feature_flags` 新表的 cold start 在 SQLite 还没建好 `config_snapshots` 时 raise；引擎默认走"flag 关闭"。**发现**：测试 `ConfigDaoFeatureFlagsTests::test_missing_snapshot_returns_default_off` 必须覆盖。**回滚**：N/A，安全默认。
- **R-F1-3 (M)**：J.4 决策的 `ExecutionIntentSource` 扩展（加 `recovery`）漏改某个未列出的消费方（例如 audit summary builder），导致 KeyError。**发现**：F.1 commit 3 必须先全仓 grep `intent.source` 与 `ExecutionIntentSource`，每处改完再合 commit；测试 `ExecutionIntentExtendedFieldsRound124Tests::test_recovery_source_round_trip`。**回滚**：把 `ExecutionIntentSource` 回退到 `Literal["manual","auto"]` + `git revert`。

### F.2 Paper

- **R-F2-1 (M)**：引擎写 `execution_events` 表的频率（每个 paper trade 写 3 条 PROPOSED/PREVIEWED/ROUTED）触发 SQLite 写入抖动。**发现**：每天复跑一次 `bench_audit_events.py` 同等级压测（针对 `execution_events` 表）；P95 > 100ms 触发告警。**回滚**：暂停 paper flag，fallback 到 batch insert（`insert_many`）。
- **R-F2-2 (L)**：`PaperIntentIdempotencyTests` 在并发场景（两个客户端同时 POST `/api/strategies/{id}/execute`）漏测；同 `intent_seq` 短时间内被分配两次。**发现**：J.1 决策的"SQLite 序列原子分配"测试必须用 `threading.Thread` 起两个 worker 跑；属于 `tests/test_persistence.py::ParameterVersionDaoTests` 的同款约束。**回滚**：N/A（属于实施期 bug 修复）。
- **R-F2-3 (M)**：Paper 模式引擎产出与 `repo.execute_strategy_signal` 旧路径在"清理 manual_execution alerts"的时序上有差异。**发现**：`PaperShadowParityTests` 与现有 `tests/test_control_api.py` 的 manual_execution 测试同时存在分歧。**回滚**：关 paper flag。

### F.3 Demo

- **R-F3-1 (H)**：J.2 真测发现 Bybit 不接受同 `orderLinkId` 复用，但 §A.1 实测时漏掉某种 race（例如第二次提交时 Bybit 在 `processing` 状态返回不同响应），引擎按"复用"假设走，结果挂双单。**发现**：审计 `exchange_order.created` 同一 `exchange_link_id` 出现两次；Demo Web UI 同一 link 出现两笔订单。**回滚**：紧急关 `execution_engine.demo` flag + Demo 上手动撤一笔；调整设计为"严禁 link_id 复用，重试用新 link_id + 服务端去重"。
- **R-F3-2 (H)**：`recent_actions` 容差 ±2 秒在某种 WS 推送延迟峰值（>5s）下错误判定为外部干预，把策略错误锁到 `external_modified` 状态。**发现**：`exchange_order.external_cancel` 计数与 Bybit Demo 真实外部撤单数对不上（实施期需要 user 在 Demo Web UI 手动制造已知外部撤单做基准）。**回滚**：临时把容差调到 ±10 秒（hot config）+ flag 不关，继续观察；或关 flag。
- **R-F3-3 (M)**：J.5 `acknowledge-drift` endpoint 鉴权漏判某种 `requested_by` 形态（例如 `system:openclaw` 这类带前缀的字符串），导致自动化 ack。**发现**：`AcknowledgeDriftEndpointTests` 必须覆盖 6+ 种 `requested_by` 取值。**回滚**：N/A，bug fix。

### F.4 Live

- **R-F4-1 (H)**：双写期 `execution.engine_diff` 持续非 0，user 不能确认 14 天稳定。**发现**：每天看 audit 计数，> 1/天 即认为不稳定。**回滚**：关 `execution_engine.live` flag，回到 paper-only/demo-only；若已在 live 上有 active orders，引擎仍能按本地 `OrderRecord` 撤改（commit 6 未提交前 oracle 函数还在）。
- **R-F4-2 (H)**：commit 6（删旧函数）已合并后发现 live 上有未覆盖的 corner case，必须 `git revert`。**发现**：审计 `execution.engine_diff` 计数突增（但此时 oracle 已删，发现机制只能靠 `exchange_order.rejected` / 用户报告）。**回滚**：硬性 `git revert` + 立即重启 + 通知 user。**缓解**：commit 6 必须 user 显式 sign-off，本路线图建议在 `docs/P0-4.2-final-cutover-2026-04-XX.md` 中签字记录。
- **R-F4-3 (M)**：J.6 `instruments-info` 重拉在 live 第一次 dispatch 时引入 ~500ms 延迟，与 50ms 策略循环冲突。**发现**：`InstrumentsCacheInvalidationOnLiveFlipTests` 必须覆盖延迟敏感断言；live 切换的当 cycle 跳过自动 dispatch 是设计预期。**回滚**：N/A，预期行为。
